## The central finding, confirmed independently

The extractor's claim is that the published article prints no comparison table and that every
model-versus-baseline comparison is a figure with no values in the text layer. Both halves hold.

The whole JATS document, parsed with `xml.etree.ElementTree` rather than with a regular expression
over the markup, holds **zero `table-wrap` elements and zero `table` elements**. It holds six `fig`
elements. The three tables of the paper are all in the SI Appendix: S1 the eight genome assemblies,
S2 test perplexity for the authors' own three models, S3 the training hyperparameters.

The SI Appendix figure pages were then scanned for every decimal number. None of them is a
comparator value. What the text layer carries is:

- axis ticks (`1.0`, `1.5`, `2.0`, `2.5`, and the integers `1` to `10`),
- the GPN score bin edges of the Figure S7 legend (`(-9.5, -8.5]` and so on, which is why the
  strings `5.5` and `7.5` occur there at all; neither is an odds ratio),
- threshold quantiles (`0.02 0.04 0.06 0.08 0.10`, `10 3 10 2 10 1`),
- method legends (`GPN`, `phyloP`, `phastCons`, `abs(phyloP)` for Figure S9; `GPN×LD`,
  `phyloP×LD`, `phastCons×LD`, `abs(phyloP)×LD`, `LD Score` for Figure S11, and the same set
  broken across lines by the rotated axis labels of Figure S12),
- the per-class rare and common counts in the Figure S9 subplot titles
  (`n=3013782 vs. 1556193` and the rest),
- the two threshold definitions printed above Figure S8
  (`Rare: AC = 1; Common: AF >= 0.01` and `Rare: AC <= 5; Common: AF >= 0.05`).

Figure S10's two panels print nothing at all beyond the letters `a` and `b`: even their axes are
rasterised. **No printed comparator value the extractor missed was found.** The paper's whole
model-versus-baseline story is in pixels, and the only comparator figure it prints anywhere in text
is the bound "less than 7.5-fold enrichment was observed for other methods", which the batch records
as `...-claim-comparator-bound-gwas`.

The supplementary zip also carries `pnas.2311219120fig01.jpg` to `fig06.jpg` and matching GIFs.
Those are raster images of Figures 1 to 6. Reading a bar height off them would be reading pixels,
which `docs/collection.md` forbids, so they were not opened for values and are not pinned.

## How the values were compared

Three passes, each able to fail on its own.

1. `npm run -s batch -- check-values` over the whole batch against the pinned JATS XML and the text
   layer. It reproduced the extractor's figures exactly: 6 `in_cell` for the Table S2 cells and 17
   `locator_not_parsed` for the prose values, with no `not_in_row`, no `wrong_column` and no
   `overclaimed_in_row`. The last of those matters here, because Table S2 prints `2.92` in two
   different rows and a value copied from a neighbour would usually show up as an overclaim.
   `value-check.tsv` in the batch folder is this pass's run.
2. `review/recheck_values.py`, written for this pass. It imports nothing from
   `extract/parse_values.py` and does not read `extract/values.json`. It re-checks the four artifact
   hashes, asserts the absence of tables, builds the article's section tree from its own
   `<sec><title>` elements, and then checks each of the 17 prose values **inside the section its
   `source_locator` names**: the value together with the label the locator names must occur exactly
   once in that section and exactly once in the whole body, and a negative control with the value
   moved to a neighbouring label must be absent anywhere. Whitespace is dropped before comparison,
   because the JATS marks up italics, maths and superscripts inside these sentences, so where a space
   falls is an artefact of the markup and not of the page. The six Table S2 cells are read by column
   position: the character span of each column's header label is taken from the printed header line,
   and a cell is the one number right of the row label whose span overlaps that column's span, so a
   value from the neighbouring column cannot match. Each locator's named row and column are then
   checked against what was read. 37 checks, all passing.
3. `review/mutation_test.py`, which confirms pass 2 bites. It drives the same script over six
   deliberately corrupted copies of the batch and all six are caught: a Table S2 chromosome-wide
   value swapped for its row's non-repeat value; a non-repeat value swapped for another row's; a
   locator's column swapped; `96%` changed to `95%`; `10.3-fold` changed to `10.5-fold`; and the stop
   codon median changed from the published `2.8` to the bioRxiv v3 value `2.81`.

All 23 results were checked, not a sample: 17 against the sentence their locator names, 6 by column
position. The descriptive claims were checked individually against their own locators in the
re-retrieved artifacts, which is where this review's two locator corrections come from (below).

Every `null` and `missing_metadata` entry was checked against the source. All of them are genuinely
unstated: no checkpoint for any of the five configurations, no parameter count, no variant totals
for the in silico mutagenesis set or the 1001 Genomes set, no window counts per gene region class,
no accession for the 1001 Genomes matrix, and no denominator for the 10.3-fold odds ratio.

## Rulings on the extractor's eight questions

### 1. Main-model assignment: upheld

The question is whether "Consequently, we focus on this model throughout the remainder of the paper
unless otherwise specified" is enough to put the headline values on the repeat weight 0.1
configuration, given that `docs/collection.md` says an unidentified model version stays at family
level and is not assigned to a specific checkpoint.

It is enough, and the collection rule does not bite here. That rule is about checkpoints: it forbids
collapsing an unidentified version into a concrete released artifact. Nothing in this batch claims a
checkpoint. All five configurations carry `checkpoint` absent with reason `unreported` and are
identified by the training recipe the paper prints, not by a released model. The question is only
which of the paper's own three training runs produced the headline numbers, and the paper answers it
three times over:

- The sentence itself, read with the one before it: "Compared to full down-weighting, moderate
  down-weighting results in a similar improvement in perplexity for nonrepetitive regions without
  sacrificing genome-wide perplexity as much. Consequently, we focus on this model throughout the
  remainder of the paper unless otherwise specified." "This model" is the moderate down-weighting
  one. Table S2 labels the three runs `Repeat weight 1`, `Repeat weight 0.1` and `Repeat weight 0`,
  and the body elsewhere names the extremes as "the model without any down-weighting" (weight 1) and
  "0.0 ... down-weighting" (weight 0), so moderate is 0.1 and nothing else.
- SI Appendix Table S3, which Materials and Methods introduces as "A list of hyperparameters is
  displayed in SI Appendix, Table S3", prints a single value: **`Repeat weight 0.1`**. The paper's
  one canonical hyperparameter table is the 0.1 model's.
- Materials and Methods describes the single-species ablation as trained "with a repeat weight of 0.1
  and the same hyperparameters", which only reads as an ablation of the default if the default is
  0.1.

Two sentences pull the other way and have to be dealt with, not ignored. "On a separate note, a
slightly higher odds ratio is achieved by the GPN model trained with an intermediate loss weight on
repeats (SI Appendix, Fig. S6C)" and "Interestingly, the GPN model trained with an intermediate loss
weight on repeats achieves the best performance (SI Appendix, Fig. S6D)". Intermediate is 0.1, so on
their face they compare the main model with itself. The reading that fits the rest of the paper is
that both sentences describe which of the three bars in those ablation panels is highest, not a
comparison with the headline number: Figure S6 is captioned "Comparison of GPN models trained with
different loss weights on repeats", and its panels c and d redraw the Figure 5c and 6c analyses for
all three models. The sentences are loosely written, not evidence of a different default. Both
sentences are present in bioRxiv v3 as well, word for word apart from the figure numbering, which
was Supplementary Figures S5c and S5d there, so the awkwardness is the authors' and not an artefact
of the published version.

The assignment stands, with the deciding sentence quoted in the configuration's `provenance_note` as
the extractor left it. The one thing worth adding for a later reader is that Table S3 is the stronger
evidence, and that is now in this review.

### 2. Single-species perplexity mapping: upheld

Materials and Methods prints "This model obtained a higher test perplexity of 3.13 (3.17 on
nonrepeat regions)" without naming Table S2's column headings, and the batch puts the two values on
the same two protocols as the Table S2 cells. That mapping holds. Table S2's caption uses the same
two words for the same two columns, "improved test perplexity in non-repetitive regions" against
"genome-wide perplexity", so the unqualified figure is the chromosome-wide one and the parenthesis is
the non-repeat one. The arithmetic agrees: 3.13 is higher than all three chromosome-wide cells (2.88,
2.90, 3.03) and 3.17 is higher than all three non-repeat cells (2.99, 2.92, 2.92), which is what
"higher" in that sentence refers to. The extractor's reading stays recorded in the evaluation's
`limitations`, which is the right place for it.

### 3. Which variant set the 10.3-fold covers: stays unreported

Upheld. The sentence cites Figure 6c, which is the contingency table, and names no variant count.
Figure 6d is `n = 453,281` "variants with whole-genome alignment" and Figure 6e `n = 510,462` for the
full set. The following sentence, "Furthermore, GPN × LD achieves much higher odds ratios when
considering the full variant set, including regions that do not align to other Brassicales (Fig.
6E)", only makes sense if the 10.3-fold is the aligned subset, so that is the likely reading. The
paper does not say it, so `denominator` stays absent with reason `unreported` on both the protocol
and the result, and the indication is recorded in the result's review note rather than in the field.

### 4. "Accuracy on CDS (96%)": upheld as accuracy

The paper writes "achieving the highest accuracy on CDS (96%) and the lowest on ncRNA (51%), the
least frequent class" and defines no per-class quantity. A per-class figure read off a confusion
matrix is usually recall, but Figure 2b, the confusion matrix that would settle it, prints no values,
so there is nothing to check an inference against. Recording the source's own word as the metric
concept, the class in `metric_qualifier` and the ambiguity in the result's `scope_note` is the
correct handling under "never guess".

### 5. "5.5-fold" and "10.3-fold": odds ratios, and the printed value keeps the "-fold"

The metric is an odds ratio from Fisher's exact test. Three places in the paper say so and the body
text's "fold enrichment" is loose wording for the same number:

- Materials and Methods, "Variant Effect Prediction": "We calculated the odds ratio and *P*-value
  with Fisher's exact test."
- Figure 5c caption, which the 5.5-fold sentence cites: "Contingency table and odds ratio showing
  enrichment of putative functional GPN scores in rare (AC = 1) vs. common (AF ≥ 5%) variants."
- Figure 6c caption, which the 10.3-fold sentence cites: "Contingency table and odds ratio showing
  enrichment of GWAS hits (for any trait) in putative functional (associated) GPN × LD scores." The
  sentence itself opens "by analyzing odds ratios (Fig. 6C)".

Fold enrichment and an odds ratio are not the same quantity in general, so this is worth stating
plainly: the authors computed an odds ratio and described it as a fold enrichment. The `odds-ratio`
concept in `data/vocab/metric.ttl` covers exactly this use, "usually the enrichment of one variant
class over another among items a predictor flags (for example rare versus common variants in the
tail of deleterious scores)", and its scope note already cites the same group's GPN-MSA paper for
the same measurement. No new concept is needed.

`printed_value` keeps the "-fold" the page prints. `docs/collection.md` asks for "the string exactly
as printed, including `%`, `±` and rounding", and "-fold" is the unit word in that sentence exactly
as `%` is in a percentage. A reader comparing `5.5-fold` against an odds ratio printed as `5.5` in
some other paper is comparing on metric, qualifier, unit and direction, none of which the string
affects. The metric decision and the wording conflict are now in each result's review note.

One smaller thing found while checking this. Materials and Methods defines common variants as "those
with allele frequency above 5%" while the Figure 5c caption prints "Common: AF ≥ 5%". The result's
`metric_qualifier` says "at least 5%", which follows the caption of the panel the sentence cites.
That is the right choice and the disagreement is noted on the result.

### 6. Correlation type: upheld as claims

`r = 0.22` against phyloP and `r = 0.13` against phastCons are recorded as claims and not results.
That is right: they measure agreement between two scores over the variants both methods score, not a
model's performance on a protocol, and there is no evaluation for them to hang on. The paper does
not say whether `r` is Pearson or Spearman and nothing was inferred, which both claims state.

### 7. Direction on the repeat-variant share: upheld as `lower`

The share of repeat variants ranked before the first decile of missense variants carries
`metric_direction` `lower`. The authors state the reading themselves: "These represent a substantial
decrease compared to the 27% observed in the model without any down-weighting", with the decrease
from 27% to 9% and 8% presented as the improvement that justifies down-weighting repeats. The
protocol's `limitations` record that this direction rests on the authors' view that repeat variants
should not outrank missense variants, which is the right place for it.

### 8. Licence: the text layer may stay

It may stay, and it was regenerated in this pass to prove it is what it claims to be.

The article and its SI are CC BY-NC-ND 4.0. Section 2(a)(4) of that licence authorises exercising the
licensed rights "in all media and formats whether now known or hereafter created, and to make
technical modifications necessary to do so", and states that such modifications never produce Adapted
Material. A `pdftotext -layout` run is a format shift of that kind: it reproduces the PDF's own text
stream and adds nothing. The No Derivatives term restricts sharing Adapted Material, so it does not
reach this file.

Two further points make it moot in practice. The archived PDF in the same batch folder reproduces
strictly more of the work than its text layer does, and the batch keeps it under the same licence on
the basis that `docs/collection.md` permits archiving source bytes for later review where the licence
allows. And the file is not decorative: without it the deterministic Table S2 parse cannot be rerun
at all, since the values are in a PDF the publisher serves only behind a per-request zip. It stays,
with the generating command recorded on the source record, which it already is
(`extraction_method`, naming poppler 26.08.0 and the text layer's hash).

This is the only `*.layout.txt` kept under `data/omics`, so there is no repository precedent either
way; the ruling rests on the licence text.

## A pre-existing error in stored data: a GPN-MSA result counted as a GPN result

The extractor flagged this and did not touch it. It is real, and this review fixed it.

`gfm-guide-20261014-config-evee-gpn-msa` is a GPN-MSA configuration by every field it carries: name
"GPN-MSA hg38 scores, pre-computed (Pearce et al. 2026)", description "Pre-computed GPN-MSA scores
downloaded from Hugging Face (songlab/gpn-msa-hg38-scores)", `reported_name` "GPN-MSA", `checkpoint`
`songlab/gpn-msa-hg38-scores`, and a `source_locator` pointing at the EVEE paper's Figure 1 column
labels, where the column is labelled GPN-MSA. Its one link was `configuration_of`
`regulatory-variant-20261009-model-gpn`, the GPN family record. GPN-MSA has had its own family record
all along, `gfm-guides-20261014-gpnmsa-model-gpn-msa`. GPN and GPN-MSA are different models: GPN is
trained on unaligned genomes, GPN-MSA on a human-centred multispecies alignment.

### What rested on it

One evaluation and one result, and nothing else:

- `gfm-guide-20261014-eval-evee-deconfounded-gpn-msa`, the only evaluation with that configuration as
  its `system`,
- `gfm-guide-20261014-result-evee-deconfounded-gpn-msa`, AUROC `0.952` on the EVEE deconfounded
  ClinVar SNV benchmark, 158,616 SNVs, 27.8% pathogenic.

So the GPN family record carried 17 results of which one, this AUROC, was GPN-MSA's. It now carries
16 of those, and 39 in all once this batch's 23 are added. Three checks bound the effect beyond
that:

- No `use_case` record has an `assessed_by` link to
  `gfm-guide-20261014-protocol-evee-deconfounded-snv-auroc`, and no judgement claim names it, so no
  use-case judgement rests on the result.
- No `discrepancy_review` claim in the store mentions GPN at all, among the 21 of them, so no
  accepted discrepancy review can be orphaned by the change. This matters because a finding's
  `systems` key is computed after `configuration_of`, `family` and `alias_of` resolution
  (`docs/discrepancies.md`), so relinking the configuration does change which systems any finding
  over this result compares. If a later knowledge-graph build changes a finding ID over the EVEE
  protocol, this is why. The current `discrepancies.json` is a build product and is not in the
  worktree, so the effect could not be computed here.
- `data/omics/gpn-star-20261116/notes.md` names the same configuration while reusing IDs, but creates
  its own configuration rather than editing this one, so nothing there depends on the wrong link.

### The fix

The fix touched one link and nothing else, so it was applied rather than escalated.

- `data/entities/configurations.jsonl`: the `configuration_of` target changed from
  `regulatory-variant-20261009-model-gpn` to `gfm-guides-20261014-gpnmsa-model-gpn-msa`. No `family`
  link was added, because the record never had one and adding it would be a second change.
- `metadata-correction-gpn-msa-configuration-of-20261116`, a claim in this batch, keeps the previous
  value in the format the existing `links` correction uses
  (`metadata-correction-a33741d0cfa1ced7c402`), with the subject linked to the configuration.
- `npm run records -- change docs/reviews/2026-11-16-gpn-paper.md data/omics/gpn-paper-20261116
  gfm-guide-20261014-config-evee-gpn-msa` recorded the change in provenance.

No value was edited and no result was superseded. The result is correct; it was attached to the wrong
model.

## Discrepancies

None involve this batch, and none can. The seven protocols are author-defined and specific to this
paper: three perplexity protocols on one held-out Arabidopsis chromosome, a gene region classification
probe, and three variant protocols scored by enrichment on Arabidopsis variant sets. No other study
in the store evaluates anything on them, and the metric and qualifier combinations are unique to this
paper, so no two-study comparison exists for a rule to fire on. `public/kg/discrepancies.json` is a
build product and the build was not run here, per the coordinator's instruction; the statement rests
on the protocol identities, not on a rule run. The one discrepancy-relevant consequence of this
review is the GPN-MSA relink, covered above.
