## How the values were compared, and the sample

`npm run -s batch -- check-values` was rerun over the whole batch against the text layer of the
re-downloaded PDF. Before the review's locator corrections it reproduced the extractor's
`value-check.tsv` exactly: 60 `in_cell`, 96 `in_row`, 67 `locator_not_parsed`, and no `not_in_row`,
`wrong_column` or `overclaimed_in_row`. After them it gives 72 `in_cell`, 84 `in_row`,
67 `locator_not_parsed`. The remaining 84 `in_row` are the whole of Table 4, whose header line the
tool cannot line up with its value columns.

The manual check is not a sample: all 198 results in Tables 3, 4 and 5 and in Figure 1b were re-read
by column position, and all 25 prose results by hand. The tool's `in_row` therefore carries no
result on its own.

`review/cell-check.py`, written for this pass without using the extractor's parser, finds each table
by its own printed header line, asserts its row labels and cell counts, and indexes each cell by
column position. Every one of the 198 printed values matched the cell its locator names
(`review/cell-check.tsv`). Because each table is anchored on its own header, a Table 4 locator
cannot be satisfied by a Table 3 row.

That matters for the shared window the coordinator flagged. Tables 3 and 4 share page 5 and their
twelve row labels, and exactly two of Table 4's 84 cells print a value that also appears somewhere
in the same-labelled Table 3 row: HyCell's Immune `0.735`, which equals its Table 3 Score S, and
PCA's Immune `0.676`, which equals its Table 3 Score S. Both are placed in Table 4's own Immune
column by the column-position pass. The other 82 cells are evidence that the tool anchors Table 4
correctly as well, since their values are absent from the Table 3 rows of the same name.

Figure 1b's column identity was fixed two ways that do not depend on the extractor. Its Mean row,
`0.700 0.662 0.657 0.655 0.634 0.631`, matches Table 3's Bio column for exactly one assignment of
six models, with no collisions; and `pdftotext -raw` prints the rotated headers as plain words in
that same order, `HyCell UCE Stack scFoundation scGPT Tahoe-x1`. The rendered page was not
inspected, which is recorded as a limitation.

Thirty-six arithmetic identities were recomputed and all hold: S against its printed weights for
all twelve Table 3 rows; Table 3's S against the unweighted mean of Table 4's seven atlases for all
twelve; and Figure 1b's column means and its Mean row against Table 3's Bio for all six models.

The 25 prose results were checked by `review/prose-check.py`, which holds the sentence a reviewer
read for each one, requires it in the pinned text layer, and checks the printed value and the

## Rulings on the extractor's questions

**1. Should the model record say only that Apache-2.0 for the weights rests on the root LICENSE's
default clause?** No, and the premise is weaker than the files are. The model record should state
Apache-2.0, as it did. The hycell `NOTICE` opens "HyCell / Copyright (C) 2026 Tencent. Licensed
under the Apache License, Version 2.0; see the LICENSE file at the root of this repository", which
licenses HyCell as a whole, not merely by default; the package README's License section says
"Apache-2.0, see the repository LICENSE" and its Install section says "The weights (64 MB,
`src/hycell/checkpoints/hycell-16m/`) are part of the package"; `CITATION.cff` gives
`license: Apache-2.0` and `pyproject.toml` `license = {text = "Apache-2.0"}`. The root LICENSE's
"Unless otherwise specified, all Tencent-authored materials in this repository are licensed under
the Apache License, Version 2.0" backs all of them, and its third-party section does not mention
HyCell or CELLxGENE. What is true is narrower than the batch said: no file names the weights file
itself, and the package ships no LICENSE of its own. The model's `licence` field and
`hycell-20261106-claim-hycell-licence-code` were rewritten to cite the NOTICE header and the README
and to state that narrower reservation, in place of "no file names the weights explicitly", which
read as though only the default clause applied. The upstream data terms are unchanged: `NOTICE`
items 1 and 2 put the Census training data, the gene vocabulary and the 512 scIB lung test cells
under CC BY 4.0.

**2. Is PCA rightly its own comparison condition?** Yes. The report excludes it from its own
ranking: Table 3's caption reads "The best value of each column among the pretrained models (all
rows except PCA) is in bold", and Section 3.1 introduces it as "As a reference without pretraining
we fit PCA to each atlas (2,000 highly variable genes of the log-normalised counts, 50 components)".
Fitting to the evaluation atlas is an evaluation-time condition, which is what
`comparison.adaptation` records, and the store already distinguishes systems fitted to the
evaluation matrix that way. A reader meeting one PCA result reaches the condition through the
configuration's `condition` and through `benchmark-pca-condition`.

**3. Should SCimilarity and scPRINT share HyCell's per-cell group?** Yes, and the batch was changed.
`comparison.adaptation` records what was done at evaluation time; in this store its values are
zero-shot, fine-tuned, probe-on-frozen-embeddings and fitted-to-the-evaluation-matrix. Pretraining
with cell-type labels is a property of the training corpus. The report itself scores the two under
the per-cell condition: Section 3.1 says each model was "run by us with its released weights and
default inference settings on the same cells", and singles out only Stack's inference
("we encode the cells of each batch together, so Stack uses batch labels at inference"). If label
pretraining blocked comparison, every other pretraining difference would have equal claim to, and
no two models in the table could be compared. So the 26 SCimilarity and scPRINT evaluations now
carry the same `adaptation` as the other 152 per-cell evaluations, and Stack's 21 and PCA's 17 stay
separate, because their conditions are genuinely at inference time.

The label training is not lost. It stays in the configuration's `condition` ("the model was
pretrained with cell-type labels"), in `benchmark-label-trained`, in the limitations of all eleven
protocols that score the comparators, and in each result's own locator, which reads
`row 'SCimilarityl' (printed 'SCimilarity' with superscript l, trained with cell-type labels)`.
A reader meeting one SCimilarity result meets it by three independent paths.

**4. Should the three new concepts coexist with `avg-bio` and `average-batch-score`?** They should
coexist now, and a later vocabulary change should make the two narrower concepts `skos:broader` of
the new ones. `avg-bio` is defined as the mean of three named metrics and `average-batch-score` as
the mean of two, both scoped to Kedzierska et al. 2025; HyCell's Bio is the mean of seven scIB
metrics and its Batch the mean of five, so reusing either would label the value with an estimator it
does not have. The new `scib-bio-conservation-score` and `scib-batch-correction-score` are generic
("mean of a stated set"), with the set in `metric_qualifier`, which is what ruling 10 asks for, and
they subsume the narrower ones rather than respelling them. `weighted-composite-score` is a generic
weighted sum with the weights in the qualifier; the nearest existing concepts,
`scmbench-integration-accuracy` and `topsis-closeness`, each fix their own components, so it is not a
respelling either. None of the three has an external match, and none appears to exist: scIB
composite scores are not in STATO, QUDT or EDAM, and the file's comparable concepts carry no match
either. All three earn their place. Adding `skos:broader` to `avg-bio` and `average-batch-score` is
not done here: those blocks are used by stored records, so the edit is its own reviewed vocabulary
change, and it is semantic only, since comparison requires identical metric keys.

**5. Is the pseudotime value at donor-mean aggregation rightly a separate protocol?** Yes. The
pooled Spearman correlation and the mean of per-donor Spearman correlations are different
statistics, and the report prints both for the same four systems: HyCell 0.937 and 0.894, Stack
0.918 and 0.879, SCimilarity 0.908 and 0.868, PCA 0.888 and 0.849. Figure 4's caption fixes which
is which: "Spearman correlation between pseudotime and stage for every embedding, over all cells
(filled) and averaged over the 12 donors (open)". One protocol would let a comparison line up a
pooled value against a donor mean as one measurement. Both protocols now state their aggregation,
and the donor-mean one names the 12 donors.

## The extractor's two judgements

**Donor effects.** Confirmed. The report's own wording is Section 6: "HyCell embeds every cell on
its own and is trained to discount donor and dataset effects, which suits comparisons of cells
across donors and studies; properties shared by all cells of a donor, such as sex or disease state,
are better read from embeddings aggregated per donor or sample", repeated in the README's Embed
section. Section 3.2 adds that Stack "draws on the other cells of a sample at inference, which helps
tasks defined per sample, such as predicting a donor's disease state or the perturbation applied to
a well; such tasks are not part of this benchmark". The issue's phrasing, that removing donor
effects may remove useful disease information, is not printed and says something the source does
not. Recording the source's wording was right.

**The 555 dataset-code entries.** Confirmed as a claim, not an evidence concern, and the claim's
wording is already accurate. Section 2.3 says the decoder's code sums "a learned embedding of the
cell's dataset (555 entries) and of its donor within that dataset (12,533 entries)", matching the
sidecar's `n_datasets` 555 and `n_donors` 12,533; Section 2.5 says the corpus is "95.0 million cells
from 555 datasets" and that removal leaves "79.5 million training cells from 532 datasets". So 555
is the Census count before removal and the difference of 23 is exactly the datasets removed. The
claim says this, and `hycell-corpus-cells` records the 95.0 million and 555 separately. Nothing here
makes a value unreliable, and scoping a concern to the model would have withheld all 223 results
over a detail none of them rests on. `notes.md` gap 6 is narrower than it reads: what the report does
not state is whether the code table keeps codes for the removed datasets, not where the 23 come from.

## Corrections made in `batch.jsonl`

The batch was not in the store, so these are edits before adding, not `records -- change` cycles.
No stored value, ID or source hash was touched, and no printed value changed.

1. **A comparison-blocking error in `aggregation`, on 13 protocols and 58 evaluations.** This is the
   substantive finding of the review, not a wording improvement. Every protocol and every evaluation
   carried "Per atlas, or the unweighted mean over the seven atlases". That is right for the four
   benchmark protocols, but the eleven downstream protocols run on the cross-tissue immune atlas
   alone, and Table 5 prints four atlases and no mean over atlases. `aggregation` is one of the nine
   `comparison` fields that decide whether two evaluations may be compared automatically, so a
   sentence that is true of the suite and false of the specific protocol does two things at once: it
   asserts an aggregation the source never states, and it makes the pooled and donor-mean pseudotime
   protocols indistinguishable on the field whose job is to distinguish them. The same class of
   defect as the HyInv interpolation caveats. Each field now states what the report states, for
   example "One value over the 3,751 cells of the four B-cell
   to plasma-cell states of the cross-tissue immune atlas" and "Computed per donor and averaged over
   the 12 donors of the cross-tissue immune atlas". The two annotation-transfer protocols gained the
   inner averaging over held-out batches. For `gd-t-split-ari` the report prints neither the number
   of cells nor whether the value is pooled or averaged within donors, and the field now says so
   rather than choosing.
2. **Thirty-eight locators named a column the source does not print under that name.** Twelve Table 3
   results and their evaluations said `column 'S'`, where the printed header is `Score S`; seven
   Figure 1b results and their evaluations said `column 'Tahoe-x1 (70M)'`, which is Table 3's row
   label, where the figure's header is `Tahoe-x1`. This was the same class of defect the extractor
   fixed for the superscripted row labels. The correction is substantive, not tidying: with the
   printed header, `check-values` places twelve more results in a cell instead of a row.
3. **A provenance note about Stack had been copied onto three unrelated models.** The records for
   SCimilarity, Tahoe-x1 and TranscriptFormer each asserted "the store's Stack entries are challenge
   submissions, not the model". The clause is correct only on the Stack record and was removed from
   the other three.
4. **The licence premise was wrong, not merely thin.** This is a correction, not a confirmation. The
   batch said the weights' Apache-2.0 "rests on the root LICENSE's default clause" and that "no file
   names the weights explicitly". Two files carry it between them: the hycell `NOTICE` licenses
   HyCell as a whole under the Apache License, Version 2.0, and the package README's Install section
   states that the weights are part of the package. The model record's `licence` and
   `hycell-20261106-claim-hycell-licence-code` now cite those, and keep the narrower reservation
   that is true: no file names the weights file itself and the package ships no LICENSE of its own.
   See ruling 1 above for the quoted text.
5. **Seven protocol descriptions** were generated from their slugs and read as such
   ("Measure: b-cell to plasma-cell pseudotime ordering, all cells on the cross-tissue immune
   atlas.", with lowercased `ari`, `nmi`, `cd4 t` and `cd8 t`). Each was rewritten as one sentence
   saying what the protocol does.
6. **A limitation the batch did not record**: the report states that the seven atlases were excluded
   from HyCell's pretraining corpus and says nothing about the ten published comparators, several of
   which are trained on CELLxGENE data. Section 2.5 defines "the corpus" as HyCell's, and Section 3.1
   says only "Every dataset and collection that contributes cells to these atlases is excluded from
   the pretraining corpus". So the comparison is not shown to be held out for the comparators. Added
   to the benchmark, the report source record and the eleven protocols that score them. It is a
   limitation of the comparison, not an evidence concern: nothing suggests a value is unreliable,
   and scoping a concern to the benchmark would withhold all 223 results, which is the over-broad
   scoping ruling 4 warns against. If anything the gap cuts against HyCell, since exposure would
   favour the comparators.

No `evidence_concerns` entry was added, and no result was superseded or marked `disputed`.

## The substance the issue demands

Checked from the result records outward, which is the lesson of ruling 3 on HyInv. A reader meeting
a single result, without opening the model record, reaches all three of the issue's points.

- **The near-tie.** Both suite S results carry a `claim_scope` saying it is not a win for either,
  that the 0.001 difference has no printed uncertainty, and that the two systems ran under different
  conditions. Nothing in the batch records a rank on S. `benchmark-headline-level` quotes the
  report's "level with" and `benchmark-readme-best-s` records that the README bolds Stack's 0.736 as
  the column's best. Both are in the source: the abstract says HyCell's overall score "is level with
  that of Stack in its recommended batch-grouped mode (0.736)", and the README's table bolds
  `**0.736**` in the S column while bolding HyCell's 0.700 in Bio.
- **The weighting.** Every result under the composite protocol reaches a `metric_qualifier` giving
  `S = 0.3 Bio + 0.2 Batch + 0.25 LR + 0.25 kNN`, and the protocol's limitations say it is a chosen
  weighting rather than a measured quantity, that another choice can reorder models whose components
  differ as HyCell's and Stack's do (Bio 0.700 against 0.657, Batch 0.527 against 0.596), and that
  Table 4 prints S per atlas without its components. All four components are stored beside S for all
  twelve systems.
- **Unequal conditions.** Each evaluation's `comparison.adaptation` states its system's condition
  and each configuration repeats it, so after the ruling on question 3 four conditions remain:
  per-cell (178 evaluations), Stack's batch-grouped inference (21), PCA fitted per atlas (17), and
  HyCell's fine-tuned annotator (4), plus the three pseudobulk-count evaluations. Every protocol's
  limitations name all of Stack's inference mode, SCimilarity's and scPRINT's label training and
  PCA's per-atlas fit. The protocols also carry "No uncertainty is printed for any value under this
  protocol", so a reader of one result meets that too.
