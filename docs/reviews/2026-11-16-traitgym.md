# TraitGym benchmark paper, independent review 2026-11-16

Batch `data/omics/traitgym-20261116`, the last part of rewire-bio/rewire-benchmark-data issue #226.
Extraction by a Claude extraction agent; this review by a separate Claude review agent that did not
extract it. No human review claimed. Receipt `data/omics/traitgym-20261116/review.json`.

The batch holds 132 results from four tables the benchmark's own metric files do not cover, the
model the paper introduces, and 25 descriptive claims. Its main result is a negative one: the
paper's Table S8 and the 156 TraitGym results already in the store are the same numbers, so nothing
was re-extracted. This review re-did that reconciliation from the paper rather than accept it, and
then applied four changes to stored records.

across all three downloads, and the text layer is what every value was read from. Three distinct
PDF hashes from three downloads of one document is the evidence; the extractor's `hash_scope` says
exactly that, names the second hash and names the text layer as the stable check, so it records the
scope of its hash honestly and is left unchanged.

The receipt's `source_artifacts` therefore carries a hash this review did not verify, and every
record's `review.artifact_sha256` carries the text-layer hash, which it did. Both are stated in the

## 2. Values

`npm run -s batch -- check-values` was re-run against a fresh text layer and reproduced the
extractor's `value-check.tsv` byte for byte: 96 `in_cell`, 36 `in_row`, no `not_in_row`, no
`wrong_column`, no `overclaimed_in_row`.

All 132 results were then re-read by `data/omics/traitgym-20261116/review/recheck_values.py`,
written for this pass and importing nothing from `extract/`. Where `parse_tables.py` splits body
lines on runs of two or more spaces, this script fixes a character-column band per table column
from the start offset of each column header token and accepts a numeric token only when its own
start offset falls inside exactly one band:

| Table | Column bands, character offsets in the text layer |
| --- | --- |
| S8 | 59 LLR, 71 abs(LLR), 88 L2 dist., 102 Cosine dist., 122 Inner prod. |
| S11 | 79 Borzoi, 92 GPN-MSA, 111 CADD, 124 Ensemble |
| 4 | 85 AUPRC |
| 5 | 113 AUPRC |
| S4 | 98 AUPRC |

Those offsets are identical on every body line of each table, including the long row labels, so
**column assignment is checked directly for all 132 results, not only for the 96 `in_cell` ones.**
The 36 that `check-values` could place only in a row are covered completely rather than sampled:
all 6 Table 4 cells, all 18 Table 5 cells, all 4 Table S4 cells and the 8 Table S11 cells of the
two traits with the longest names. The two long S11 rows put their first value at offset 79, the
same band as every other row, which is what settles the mis-split the repository's own reader
produces on them. Table S4's four cells are distinguished by their dataset label, which sits in the
label zone of the same line. Result: 132 of 132 agree on `printed_value` and `numeric_value`,
0 mismatches, in `review/recheck-values.tsv`. Each of the 132 locators is distinct and claims one
cell.

Three negative controls confirm the script is a cell check and not a row check:

| Control | Outcome |
| --- | --- |
| Two values swapped inside one Table S11 row | exactly those 2 results rejected |
| One value copied into a neighbouring column band, same row | exactly that 1 result rejected |
| One Table S11 row's values shifted one column left | rejected at parse, with the offending offset named |

Independently of both scripts, all 100 cells of Table S8 were transcribed by hand into
`review/s8-reviewer-reading.tsv` before `extract/comparison.tsv` was opened beyond its header, and
all 36 `in_row` cells were read by eye from the text layer. The hand reading of Table S8 agrees
with the band parse in all 100 cells.

`missing_metadata` and the nulls were checked against the source. Tables 4, 5, S4 and S11 print no
standard error, state no chromosome aggregation basis, and Table S11 does not say whether a cell is
zero-shot or linear probing. All three are recorded as `unreported`, which is right: none of them
is stated anywhere in the paper.

## 3. The 100-cell reconciliation, three ways

`review/reconcile_s8.py` re-did it with the cell-to-metric-file mapping written out again from the
paper's model labels and the benchmark's file naming, not reused from `compare_s8.py`. The
reviewer's own reading of the paper is the paper side. Four comparisons over all 100 cells, every
one with no differences:

| Comparison | Differences |
| --- | --- |
| Reviewer's paper reading against the stored full-precision value rounded to 3 dp | 0 |
| Reviewer's paper reading against the extractor's `paper_value` | 0 |
| Reviewer's rounding against the extractor's `stored_value_rounded_3dp` | 0 |
| Reviewer's cell-to-stored-result mapping against the extractor's | 0 |

Full table in `review/reconcile-s8.tsv`. **The extractor's claim that nothing differs holds, and it
no longer rests on the extractor's reading.**

The protocols are the same, which is what makes the comparison legitimate. Appendix B.4, page 24:
"To allow easy comparison, we also use the weighted average AUPRC to evaluate zero-shot scores,
even though it is not strictly necessary." The main text confirms the direction, page 7: "We also
report similar results for zero-shot scores when using a global AUPRC rather than a weighted
average over chromosomes (Supplementary Figure S7)." So the weighted average is Table S8's basis,
and the global AUPRC is the variant kept in a supplementary figure.

One thing the extractor overstated. It says the embedding columns correspond to the `Embeddings.*`
files "and not to" the six `InnerProduct` and `EuclideanDistance` files, citing one discriminating
cell. Only one of the six is discriminated by a printed value:

| --- | --- | --- | --- |
| `GPN_final_EuclideanDistance.plus.score` | 0.345 | 0.3449957 | 0.3469633, rounds to 0.347 |
| `GPN-MSA_InnerProduct.minus.score` | 0.301 | 0.30112524 | 0.30112190, also 0.301 |
| `Caduceus_InnerProduct.minus.score` | 0.131 | 0.13107643 | 0.13107530, also 0.131 |
| `GPN_final_InnerProduct.minus.score` | 0.169 | 0.16931777 | 0.16922307, also 0.169 |
| `HyenaDNA_InnerProduct.minus.score` | 0.165 | 0.16481699 | 0.16481687, also 0.165 |
| `NucleotideTransformer_InnerProduct.minus.score` | 0.185 | 0.18491587 | 0.18486366, also 0.185 |

For the five `Inner prod.` pairs the printed value is consistent with either file. The
reconciliation is unaffected, since the paper's cell matches both, and the mapping is still right:
`Embeddings.minus.inner_product` is the set the benchmark publishes for both datasets, and the

five, not on the number. The reconciliation claim
`traitgym-20261116-claim-paper-agrees-with-benchmark-metric-files` now says so, and also names the
six duplicates in its list of what the paper prints no value for.

## 6. Rulings on the recommendations

### 6.1 The stored limitation that says the paper's table is unweighted. Wrong; fixed

`lit-genomics-20261011-traitgym-source-hf-metrics`, `attributes.limitations[1]` said: "The paper's
Table S8 prints rounded zero-shot AUPRCs on a related but unweighted basis and was not extracted."

The deciding text is Appendix B.4, page 24: "To allow easy comparison, we also use the weighted
average AUPRC to evaluate zero-shot scores, even though it is not strictly necessary." Page 7 puts
the global AUPRC in Supplementary Figure S7. The entry is wrong, and it is the kind of wrong that
costs a reader something: it says the paper's values and the stored values are on bases that cannot
be compared, when they are the same 100 numbers at lower precision. Replaced with text that quotes
Appendix B.4, states that all 100 cells match, and points at this batch. The previous text is kept
in `metadata-correction-traitgym-20261116-hf-metrics-source-limitations`.

### 6.2 Relink the eight `GPN_final` configurations to GPN-Promoter. Made

The benchmark's `GPN_final` is the paper's GPN-Promoter. Table 2 lists GPN-Promoter among the
benchmarked self-supervised models with the reference "This work", 152M parameters and a 512 bp
window, and lists no GPN row at all. Section 5: "We introduce a new gLM, called GPN-Promoter,
trained using the genomes of 434 animal species, following the training objective of GPN (Benegas
et al., 2023) and the ByteNet convolutional architecture." Appendix B.2 and Table S6 give its
training set and hyperparameters, and the availability statement gives its weights as
`songlab/gpn-animal-promoter`. The 10 GPN-Promoter cells of Table S8 equal the `GPN_final_*` metric
files at three decimal places, which ties the file prefix to the model.

The reason this is not cosmetic is in docs/discrepancies.md: "A configuration is compared as the
model it configures (`configuration_of`, then `family`, then `alias_of`)." While the link stood, 14
stored results read as results of GPN, a model this paper never benchmarks. The eight
configurations are relinked to `traitgym-20261116-model-gpn-promoter`, each with a correction claim
`metadata-correction-traitgym-20261116-config-gpn-final-*` that keeps the previous target and backs
the new edge with the paper's text.

### 6.3 GPN-Promoter's identity edges. None added, and that is a decision, not an omission

The same sentence decides it. A `family` edge from GPN-Promoter to
`regulatory-variant-20261009-model-gpn` would resolve these configurations through `family` back to
GPN and undo the relink of 6.2. The paper says only that GPN-Promoter follows GPN's training
objective and the ByteNet architecture, which is not a shared checkpoint or a shared training set:
GPN-Promoter is 512 bp promoter windows of 434 animal genomes. The model stands alone.

Its `entity_level` of `family` with one named checkpoint is upheld: `gfm-guides-20261014-gpnmsa-
model-gpn-msa` does exactly the same, `family` with `access` naming `songlab/gpn-msa-sapiens`, and
the paper identifies no revision. `facets.method_types` was missing and is added as
`foundation_model`, which every comparable model record in the store carries.

### 6.4 Add the paper to the benchmark's `source_ids`. Made

`lit-genomics-20261011-traitgym-benchmark-traitgym` rested only on the metrics table: its `version`
is a Hugging Face revision and its `scope_note` the paths of the metric files, while its
`description` states trait counts the metric files never print. The paper is where the datasets, the
matching, the splits, the allowed inputs, the metric and the leakage controls are defined, and the
21 benchmark claims this batch adds carry that definition. A benchmark record holds no measurement,
so a second source on it does not duplicate a value the way a second source on a result would.
`version` and `scope_note` are left alone: they correctly describe the pinned metric files the 156
stored results were read from. Claim
`metadata-correction-traitgym-20261116-benchmark-source-ids`.

### 6.5 `companion_of` from the metrics source to the paper. Made, and it matters more than the extractor said

`shared/omics/relations.ts`: `companion_of` runs source to source, "One study; never merges
results", and docs/discrepancies.md counts studies, not rows: "a paper that reports 150 numbers is
one opinion". Without the link, the paper's 132 results and the metrics table's 156 are two
studies, so one verdict these three authors reached from one analysis would be counted twice in the
ordering-reversal and gap rules. That is the case the rules' own `split_study_candidates` report
exists to find, and the reconciliation of section 3 is the evidence that the two sources are one
piece of work: the availability statement gives the benchmark as the same Hugging Face dataset the
metric files come from, and all 100 shared cells agree. The edge is declared in one direction only,
from the companion to the paper, so it goes on the stored record. Claim
`metadata-correction-traitgym-20261116-hf-metrics-source-companion-of`.

What this changes in the findings could not be computed here: `public/kg/discrepancies.json` is a
build product and the knowledge-graph build was not run. No accepted `discrepancy_review` claim in
the store names TraitGym or GPN, so no accepted review can be orphaned. Worth watching on the next
release: merging the two sources into one study also means one configuration per model across the
merged study's groups, which can change which configuration represents Borzoi and GPN-MSA.

### 6.6 Recheck the Hugging Face revision. Done, nothing to change

Revision `1fde19555fe8c0a55b1382bdf4c6f7082209f566` still exists, the API reports the same commit
sha and `lastModified` of 2025-03-25, and the archived bundle
`data/omics/lit-genomics-20261011-traitgym/artifacts/traitgym-metrics-bundle.json.gz` unpacks to a

Five of its 156 CSVs were re-fetched from the pinned revision and hashed byte-identically to their

The source record's `hash_scope` warning about Hugging Face mutability stays, because it is true in
general; the recommendation is closed, not left open.

## 7. Scoping of the new records, and whether anything could pool

**The new model and the 15 configurations are correctly scoped.** GPN-Promoter is one model the
paper introduces and the store had its scoring configurations without it. The 15 configurations are
`configuration_of` the stored Borzoi record and each stands for the predicted tracks of one tissue
or cell line, which is what Table 5's rows are; their `method_types` are filled, as the use-case
pages need.

**No new result can pool with a stored one.** A comparison needs the same protocol, dataset, metric,
unit, qualifier, split and direction. Every one of the 132 sits on one of eight new protocols with a
qualifier none of the stored results carries:

| New qualifier | Stored qualifier |
| --- | --- |
| best of zero-shot and linear probing; single trait; chromosome aggregation unreported | weighted average over chromosomes of per-chromosome AUPRC; subset 'all' |
| highest AUPRC among the Borzoi tracks from one tissue; single trait; chromosome aggregation unreported | as above |
| single CADD input feature as the score; chromosome aggregation unreported | as above |
| global AUPRC over all variants; single matching feature as the score | as above |

The two tables that use the full datasets rather than a trait subset, Table 4 and Table S4, are the
only place the question is close, and they are also clear. Table 4's systems are single CADD input
features, which are new `method` records, and its two conservation features are not the stored
`phyloP-241m` and `phastCons-43p` configurations: Table 4's ZooVerPhyloP is 0.673 on Mendelian
traits where the stored phyloP-241m is 0.696, and its ZooPriPhyloP is 0.225 on complex traits where
the stored phastCons-43p is 0.237. The CADD-bundled annotation and the separately downloaded bigWig
are different systems, as each method record's `identity_scope` says. Table S4's four features are
the matching features, which nothing else in the store scores. The extractor's choice to create
protocols rather than reuse the stored two is what holds this apart, and it is upheld.

The pooling risk that was real is the study-level one of 6.5, which the `companion_of` link closes.

## 8. The extractor's other questions

1. **Table S8 not re-extracted as results.** Upheld. Writing the paper's rounded values as 100 more
   results would put two records of one measurement, one system and one protocol in the graph from
   one piece of work, which downstream reads as two independent agreeing measurements. The same
   call was made and upheld in `docs/reviews/2026-11-16-gpn-msa-published.md`. One claim plus
   `extract/comparison.tsv` is the right vehicle, and this review's `review/reconcile-s8.tsv` is a
   second, independent copy of the comparison.
4. **Which lightweight ensemble.** Upheld, and on better evidence than the extractor gave. It cited
   Figure 8, where this ensemble scores highest. The paper actually defines the term, Section 6:
   "we do see small improvements when ensembling CADD with a reduced number of features from other
   models (LLR for GPN-MSA and 'l2 of l2 scores' for Borzoi), which we refer to as 'lightweight'
   feature ensembling (Figure 8)." That composition is `CADD+GPN-MSA_LLR+Borzoi_L2_L2`, the system
   the batch records, so naming it is reading the paper's definition and not choosing the best bar.
   The method's `provenance_note` and the eight results' `limitations` now quote the definition and
   still say the Table S11 caption does not repeat it.
5. **Table 5's construction.** Extraction with the rule stated is preferable to recording the table
   as a gap. Every cell is a printed number with a named trait and tissue; the selection on the
   reported variants and the unnamed track are recorded in the protocol's `selection_bias`, in the
   `metric_qualifier` and in every result's `limitations`, and the new qualifier keeps the values
   out of any comparison. A gap would lose 18 printed values and record nothing about the bias.
6. **Table 4 and S4 as methods.** Right as made. An evaluation's `system` accepts a configuration,
   model, method, pipeline or service, and `baseline` is not among them, so a `baseline` record
   could not carry these evaluations. Adding `baseline` records alongside would create a second
   entity per feature with nothing attached to it.
7. **Protocol proliferation.** None of the eight can be folded into the stored protocols without
   losing its rule. Each fixes a different selection: best of two adaptations per trait, best track
   within a tissue, top feature per category, global AUPRC on a matched feature. Folding any of
   them in would make its values comparable with the stored whole-dataset numbers, which they are
   not.
8. **`metric_qualifier` wording.** Confirmed as wanted. The qualifiers are what stop these 132
   results joining the stored comparison groups, which is the intended behaviour and the subject of
   section 7.
9. **The 36 `in_row` results.** Covered completely in section 2, not sampled.
