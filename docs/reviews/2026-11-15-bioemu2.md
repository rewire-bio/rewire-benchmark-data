## How the claims were checked

There is no `value-check.tsv`: `npm run batch -- check-values` works on results, and this batch has
none. Three passes replaced it, all scripted in `data/omics/bioemu2-20261115/review/`.

1. `review/check-tables.py` parses the model card's two printed tables again, from the re-retrieved
   file and without using `extract/parse_model_card.py`. All nine model summary rows and all twelve
   training data rows map one to one onto claims, every cell matches, and no row of either table
   and no claim is left over. Zero disagreements.
2. `review/check-claims.py` matches every claim sentence against the normalised text of its own
   sources. 42 of the 75 claims are word for word in their source. The other 33 were listed and
   read by eye at their locator: thirteen are table cells reflowed into prose, already cleared by
   pass 1, and twenty join two printed sentences, strip a markdown link or code span, or respell an
   en dash, a micro sign or a multiplication sign. Each respelling is noted on its own claim.
3. `review/check-locators.py` counts the sentences, paragraphs and bullets a locator names. Five
   locators were wrong and are corrected (below). Every other ordinal locator holds: the three
   capability bullets, the six evaluation-methodology paragraphs, the twelve training-data rows and
   nine summary rows of the model card, the README bullets and sentences, and the two
   context-parallel system-requirement bullets.

`missing_metadata` was checked entry by entry against the sources. Every `null` and every missing
reason is genuinely unstated: the model has no version row, the evaluated checkpoint is unnamed,
no GPU memory figure is printed at any system size, and throughput appears only as linked images.

## No numeric evaluation value exists

Confirmed independently, by reading all thirteen artifacts and then grepping them for the metric
names the model card's own evaluation methodology uses (RMSD, TM-score, lDDT, DockQ, coverage,
divergence) and for the usual score words. Every hit is the prose of the evaluation methodology
section itself, in both copies of the model card. The four evaluation settings are described with
no figure of any kind; the two context-parallel throughput plots are linked PNGs with no printed
numbers. The numbers that do appear are a parameter count, training-set sizes, token capacities on
named hardware, a checkpoint byte size, library versions and model hyperparameters: none is an
evaluation of the model's quality on a task. So the extractor missed nothing, and no result is
owed. Recorded as a gap for a batch that finds published numbers.

The store was grepped again for BioEmu under any spelling, across `data/entities` and
`data/evidence`: nothing. The pinned artifacts name no predecessor either, so the absent `family`,
`variant_of` and `supersedes` links are right.

## Rulings on the extractor's questions

**1. The hardware disagreement: keep the per-configuration treatment, add no evidence concern.**
The two statements, at the same commit:

- `MODEL_CARD.md`: "BioEmu-2 has been tested using NVIDIA GPUs, with an 80 GB A100 being the
  smallest tested device."
- `README.md`: "We have tested V100 (compute capability 7.0), T4 (7.5, with the CUDA 12
  installation), A100 and RTX A6000 (8.0 and 8.6), and B200 (10.0); other eligible GPUs have not
  been verified end to end."

A V100 and a T4 are smaller than an 80 GB A100, so the two cannot both be read as the model's
testing floor. They need not be about the same thing: the README's list is the package's GPU
compatibility testing, selected by install extra, and the same README ties the benchmark metrics to
an interpreter, not a device ("We tested BioEmu2 and evaluated its benchmark metrics with Python
3.12"). The sources do not say which campaign the model card's sentence describes, so declaring a
contradiction would be reading past them. An `evidence_concerns` entry scoped to the two
`hardware_tested` claims would withhold both claims (`docs/collection.md`: a named claim withholds
that claim), leaving a reader with nothing where the batch currently gives both statements with
their own locators, the conflict in `accelerator_details`, and no minimum on the model record.
Concerns are for a problem that should block comparison; nothing in the store compares a hardware
statement, and neither artifact prints a memory figure a comparison could use. So: no concern. Both
claims' notes already name the other statement, which is what a reader needs.

**2. Entity level: `family`.** Decided by the sources plus the rule. The model summary table has no
version row, and the evaluation methodology says only "We use the same model checkpoint to evaluate
all benchmarks", naming none. `docs/collection.md`: "An unidentified model version stays at family
level and is not assigned to a specific checkpoint." `missing_metadata.checkpoint_revision` records
why. `bioemu2-preview` stays a configuration, the one the Hugging Face revision publishes and
`docs/checkpoints.md` calls the default download.

**3. The three sampling modes stay configurations of the model, linked flat.** `docs/sampling.md`
says "BioEmu2 was trained for two different tasks, structure prediction and equilibrium sampling",
and its table selects different settings per mode: "Heuristic sharpening with `step_scale=1.5`"
against "`step_scale=1.0`, without sharpening". That is a configuration in the sense
`docs/collection.md` uses, so keeping them is right, and the settings claims alone would lose the
record a future evaluation has to link its `system` to. Nesting them under
`config-checkpoint-bioemu2-preview` is permitted by `relations.ts` (`configuration` is a model
subject kind) but would assert that the modes are properties of that weights file, which no source
says: the documentation attributes them to BioEmu2 and to the command line. Each mode already names
`bioemu2-preview` in its `checkpoint` attribute, so nothing is lost. Flat links also keep the modes
comparable if a second checkpoint is released.

**4. The Boltz-1 test set: no link, no protocol.** The model card says folding quality is measured
"on the Boltz-1 test set" and compared "against a range of state-of-the-art cofolding models". That
is a name with no version, no split, no target count and no named baseline, and no value was
printed for it. The store's `reported-dataset-e45a5a140888ee` ("Boltz-1 structure test set",
`needs_review`) carries `version`, `split` and `accession` as `unextracted`, so linking it would
match two unpinned identities to each other. There is also no relation that would carry the link: a
`claim` links only a `subject`, and `uses_data` runs from a task, protocol or baseline. A protocol
would have to fix a split the source does not state, and would stand with no evaluation on it. So:
nothing created. `reported-dataset-e45a5a140888ee` remains the ID to reuse when a source prints the
numbers, which `notes.md` and this review record.

**5. The publisher's LFS digest is acceptable in `checkpoint_sha256`; the 2 GB file was not
downloaded.** The pointer served at the pinned revision publishes `oid
sha256:3b4ba9236b7b458f47b40b694847b6bb4110c744becd6d2c53de7b1d04c07a81` and `size 2047661181`, and
the Hugging Face API listing for the same revision repeats both in `siblings[].lfs`, so two pinned
publisher artifacts agree. `docs/collection.md` says to hash the artifact the values come from: no
value in this batch comes from the weights, since nothing was run. The configuration states the
provenance in its own `limitations`, and `weights_sha256` carries `unextracted`. Computing the
digest locally is recorded as a gap for a batch that runs the model, not a condition on storing
this one.

**6. No claim for the absence of results.** It is an observation about the source, not a statement
the source makes. It is recorded in `notes.md`, in the ledger `gaps`, in the model card source
record's `limitations` and in the receipt, which is where `docs/collection.md` tracks what was not
covered. For consistency, `claim-model-card-publication` ("the two carry the same text") is kept,
although it is also an observation rather than a quotation: both artifacts it names are its own
sources, the statement is a byte comparison of them, and it is verifiable from the pinned bytes.
This review repeated it: the Hugging Face README is the repository `MODEL_CARD.md` preceded by a
four-line YAML front matter block setting `license: mit`, and nothing else differs. The absence of
results is not verifiable in the same way, because it quantifies over everything the source does
not contain.

**7. Claim granularity: keep all 75.** Each has its own locator, which merging would blur, and the
cost of a claim is one line. One correction to `notes.md`: it says the five README feature bullets
are kept separate, but only four are claims. The second bullet, "equilibrium sampling and structure
prediction from the command line or Python", has none. No new claim was added, because
`claim-two-trained-tasks` and the two mode configurations carry that fact with locators of their
own.

**8. The earlier BioEmu: yes, a separate batch.** The store holds no BioEmu record and no BioEmu
identifier, so there was nothing to reuse here, and the pinned artifacts name no predecessor, so no
relationship could be recorded from them either. Registering BioEmu (2025) needs its own pinned
paper; the `scope-audit.jsonl` entry defers it to a discovery pass, which is the right record.

## Gaps after review

The extractor's ten gaps stand as written. In addition:

1. No numeric evaluation value exists anywhere in the pinned sources, so BioEmu-2 enters the store
   with descriptive claims only and supports no comparison with any other model. Until a source
   prints numbers, no use-case judgement can rest on it.
2. The checkpoint bytes are unhashed locally; two publisher statements of the digest agree.
3. The folding protocol and the Boltz-1 test set identity are unresolved, and
   `reported-dataset-e45a5a140888ee` is the ID to reuse.
4. OriDynamics (arXiv:2611.11958), which names BioEmu2 as a baseline, is the one known third-party
   evaluation and was not retrieved. It is the most likely source of a first result for this model.
5. `build.py` reproduces the extraction state of the batch; `review/apply-review.py` turns that into
   the reviewed state. Together they rebuild what was stored.

No discrepancy involves this batch: the knowledge-graph rules work on results, and it has none.

Nothing in the batch was wrong on a fact. Five locators were corrected, the review objects were
