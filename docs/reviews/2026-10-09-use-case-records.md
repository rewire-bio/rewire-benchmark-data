# Use cases as records: independent review, 2026-10-09

Reviewer: a separate Claude review agent that did not write the migration. No human review is claimed.

Scope: batch `data/omics/use-case-records-20261009/` (26 `use_case` records, 100 relevance judgement claims), `deriveUseCaseInputs` and `judgementPins` in `shared/omics/use-cases.ts`, `scripts/omics/migrate-use-cases.ts`, `scripts/omics/repin-use-cases.ts`, `docs/use-cases.md`, and the ontology additions. The baseline is `data/omics/use-cases/inputs.json` and `sources.json` on `origin/main`.

All checks used scripts written for this review; the author's round-trip claim was not relied on.

## Outcome

The migration is faithful. The records hold every field of the old inputs, and the derived inputs equal the old inputs. The ontology additions are accurate apart from three wording points. The new gate is weaker than the old one: several changes that used to withhold an active mapping now leave it active. That is a design question for the maintainers, recorded below as findings 1 and 2. Fix or explicitly accept those two before merge.

## Checks and results

1. **Round trip.** `deriveUseCaseInputs(loadRecords())` compared field by field with `origin/main` `inputs.json`: 26 of 26 use cases and 100 of 100 mappings identical, including `evidence_sha256`, `lifecycle`, `reason` and review. The only difference is `evaluation_ids` order, in 37 mappings; sorted, the lists are equal.
2. **Record fidelity.** Every use-case field (title, area, contexts, search terms, intended users, decision, inputs, output, setting, exclusions, clinical scope, evidence gaps, collection plan, planned work) and every mapping field (relevance, endpoint, rationale, constraints, limitations, revision, reason, task_id) is present and equal. Citations equal `citation_locators`, and `source_ids` equal the set of cited sources. Review method, time and note match, and `reviewer_note` equals the old actor text verbatim in all 126 records. The `assessed_by` links of each use case equal the set of its mapped protocols. The batch equals the records in the store. `excluded_evaluations` equals exactly the protocol evaluations missing from the old mapping for all 100 judgements: three on `use-case-mapping-20260930-339-25925e279972` and two on `use-case-mapping-20260930-349-1af09c2e0e0f`, none elsewhere. The four documentation source records from the retired `sources.json` are in the store with the same content in the declared-attribute shape (`review_scope` moved into `review.scope`).
3. **Reviewer keys.** Eight distinct actor strings. Each named agent is captured: "Codex ..." gives `codex`, "Claude Sonnet ..." gives `claude-sonnet`, "Claude (Opus 5.5) ..." gives `claude`, and strings naming both give both. See finding 9 for one caveat.
4. **Lifecycle.** The 97 active mappings are `source_checked` claims and the 3 drafts are `needs_review` claims. Derived output and the built release `2026-10-09-c71d39c6cf9d` (`use-cases.json`) have 97 active and 3 draft, with the same three draft IDs.
5. **Gate semantics.** Compared `deriveUseCaseInputs` and `evaluationBlocker` with `validateMapping`, and probed the behaviour by editing an in-memory copy of the store and running both `deriveUseCaseInputs` and `buildUseCaseArtifact`. Per evaluation, `evaluationBlocker` applies the same checks as `validateMapping` with active checks. The new "no eligible evaluation" blocker and the clean-source check on every cited source are stricter than before. The weaker points are findings 1 to 5.
6. **Ontology.** `rb:UseCase`, `rb:RelevanceJudgement` (subclass of `rb:Claim` and `obo:SEPIO_0000001`), `rb:assessedBy`, the `use_case` class and `assessed_by` relation in `mapping.json`, the `relevance` field and scheme, `context.ttl` `research`, `context.jsonld` terms, `build.py` `PROTECTED` and the `export.ts` typing all agree. Re-downloaded `http://purl.obolibrary.org/obo/sepio/releases/2023-06-13/sepio.owl`: SHA-256 `ae9161620d677fe16857e0704006b7d07086e2ac75688261be901b0f9c3db488`, equal to `source_sha256`. Re-running `scripts/kg/extract_terms.py` on it reproduces `sepio-subset.nt` byte for byte. SEPIO_0000001 is defined as "a statement made by a particular agent on a particular occasion that a particular proposition is true, based on the evaluation of one or more lines of evidence". A relevance judgement is an agent's dated statement that a protocol bears on a use case to a given degree, made after reading the sources, so the subclass claim holds. The basis notes on external terms were checked against OLS and schema.org: IAO_0000005 and IAO_0000104 are directive information entities, NCIT C81930 "Use Case" describes user and system interaction steps, and schema:Question is a subclass of schema:Comment. See finding 7.
7. **Commands.** `npm run records -- check`: 29,443 records match their provenance (exit 0). `npm run typecheck`: exit 0. `npm run test:kg`: 24 tests OK. `npx vitest run tests/use-case-records.test.ts`: VITEST_RESULT.

## Findings

Probes below use `use-case-map-gears-norman-table6-mse` unless named. "Old" means `origin/main`, where `evidence_sha256` fixed at review time covered every dependency record in full, so any change to one withheld the mapping.

1. **High. The evaluation set is live, so a reviewed comparison can lose members while the judgement stays active** (`shared/omics/use-cases.ts:492-516`). Marking one of the four evaluations `disputed`, or disputing its configuration, gives an active mapping with three evaluations. The judgement's rationale names the complete comparison ("includes a no-change control, CPA, CPA with knowledge-graph features and GEARS"), so dropping a member changes what the published mapping supports. Changing a result value also leaves it active. Old: withheld. Adding new evaluations without review is documented and tested as intended; silent removal is not documented. Suggested fix: record the reviewed evaluation set (or pin it) and withhold when a previously included evaluation drops out, leaving additions as designed.
2. **High. The pin set misses fields that carry meaning** (`shared/omics/use-cases.ts:388-411`). These changes all leave the judgement active: protocol `description` or `name`, use case `facets.contexts` changed from `research` to `clinical_research`, use case `setting`, protocol link relation changed from `part_of` to `supersedes`, and the `artifact_sha256` of a cited source that is not a protocol source. Of the 98 mapped protocols, 23 have neither `attributes.protocol` nor `attributes.version`, so their pin covers only status and link targets; their definition is in `name` and `description`. Not pinned on any protocol: `metric`, `metric_direction` (15 protocols), `dataset`, `task`, `comparison_panels`, facets. Not pinned on use cases: name, description, setting, clinical_scope, intended_users, contexts. Cited sources outside the protocol's sources are unpinned in 12 of 100 judgements, and 16 use cases cite a source that none of their judgements pins. Old: withheld in every case. Suggested fix: pin protocol name, description, facets and the attributes other than review and locator fields; pin use case name, description, facets and all decision attributes; pin every source in `claim.source_ids` and the use case's `source_ids`. Pinning link targets only and not relation names is reasonable for renames, but a pin on `(relation, target)` pairs after relation normalisation would keep the #50 behaviour and catch a change of relation.
3. **Medium. Some gate failures that used to withhold now stop the release** (`shared/omics/use-cases.ts:512`, `:338`, `:371-374`). With `catalog-task-mfass-splice` disputed, `deriveUseCaseInputs` keeps `use-case-mapping-splicing-mfass-matched-v1` active, and `buildUseCaseArtifact` then throws "Active applicability cannot target an inactive task". A use case's own cited source gaining an evidence concern makes `validateEntries` throw for that use case's other active mappings. Old: those mappings were withheld. This fails closed, but blocks every release until fixed. Suggested fix: check task status and the use case's cited sources in `deriveUseCaseInputs` and withhold.
4. **Medium. `use-cases:repin` re-pins every reviewed judgement that no longer matches** (`scripts/omics/repin-use-cases.ts:22-31`). `docs/use-cases.md` step 3 tells reviewers to run it to record pins for a newly reviewed judgement. Run then, it would also re-pin any judgement withheld for a real change, which re-activates it without review. Suggested fix: take explicit claim IDs, or re-pin only claims that have no pins.
5. **Medium. Withdrawal no longer leaves a tombstone, and the release guard does not see it** (`shared/omics/use-cases.ts:499`; `scripts/release/next.mjs:62-64`). A claim set to `excluded`, `superseded` or `disputed` is dropped from the artifact; the old contract kept a `withdrawn` tombstone with `prior_release_id`. `next.mjs withheld` checks only for `needs_review`, so a served mapping that disappears passes. `deriveUseCaseInputs` also throws while the use case still links `assessed_by` the protocol, which `docs/use-cases.md` step 4 does not mention, so a reviewer marking a judgement `disputed` breaks the build. No tombstone exists today, so this does not affect the current data.
6. **Low. Silent truncation at 100 evaluations** (`shared/omics/use-cases.ts:496`, `:516`). `use-case-mapping-20260930-337-fa51fe46268a` already has 97. Since additions are automatic, four more evaluations on `uc20260930-proteingym-amfr-protocol` would drop IDs without notice. Throw or withhold instead.
7. **Low. Ontology wording.** (a) `rb:assessedBy` (`data/ontology/rb.ttl`, and the basis in `data/ontology/mapping.json`) says the link holds only when a reviewed judgement backs it, but the three draft judgements' links are asserted in `use-case-cnv-detection-characterisation` and will be exported. (b) `rb:RelevanceJudgement` says it is "a claim that a protocol's evaluations are evidence for a use case", which does not fit an `outside_scope` judgement. (c) It says "other claims are study findings", but about 1,170 claims are curator assertions about links (`links:part_of`, `links:family` and others), not study findings. (d) The basis says SEPIO has_evidence starts from an assertion; its domain is proposition or assertion. None of these affects the subclass claim.
8. **Low. `not_assessed` is allowed by the mapping schema but missing from `data/vocab/relevance.ttl`.** `docs/use-cases.md` lists three values. Choose one and make the schema and vocabulary agree.
9. **Low. `reviewer` lists workers as well as reviewers.** For 29 records the actor text names a worker and a separate reviewer (for example "Claude Sonnet AMP-integration worker ... independently reviewed by Codex"), and both become reviewer keys. Unnamed reviewers ("independent worker cross-review", "root integration review") are not represented. `reviewer_note` keeps the full text, so no information is lost.

## Must change before merge

Findings 1 and 2, or an explicit maintainer decision to accept them with the doc and test stating what no longer withholds a judgement. Findings 3 and 4 are small fixes and should go in with this change. The rest can follow.
