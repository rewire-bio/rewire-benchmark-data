# Use-case baselines: independent review, 2026-10-12

Batch: `data/omics/use-case-baselines-20261012/` (26 `baseline` claims, one per use case; issue #121). The proposer's report with its open decisions is `report.md` in the same folder.

Reviewer: a separate Claude review agent that did not propose these claims. No human review is claimed. Nothing was executed or reproduced. This is a check of each claim against its cited sources and the store.

## Outcome

- All 26 claims are approved and set to `source_checked`. 2 are accepted as proposed (genetic perturbation response, therapeutic target validation). 24 are corrected: the rationale in all of them, the value in 2, and the source list in 6.
- Each claim is pinned with `npm run use-cases:repin -- docs/reviews/use-cases/baselines-2026-10-12.md <ids>`. All 26 publish.
- 10 use cases get an evidence-gap sentence: 6 where no comparison scores a machine-learning method beside the baseline, and 4 where only one part of a two-part baseline has such a comparison.
- 6 use cases get no gap sentence because the only obstacle is a missing or wrong method-type tag. These records are listed below for a separate reviewed PR. No tag is changed here.
- No method record was added. No numerical value or result was changed.
- `claimPins` pinned any reviewed claim with field `baseline`, including the older descriptive claim `structural-20261009-claim-smorodina2026-random-baseline` on a protocol. It now pins only baselines whose subject is a use case, and that claim is restored unchanged.
- After merging main, the MassSpecGym in the Wild judgements added a random-ranking row to the mass-spectrum use case. Its rationale was corrected again (below) with `records -- change`. Every other comparison count is unchanged.

## How the check was done

1. Re-retrieved every cited source (Europe PMC full-text XML, PMC, publisher pages, arXiv, ACL Anthology, the TREC runs browser) into empty scratch directories and compared SHA-256 with `artifact_sha256`.
2. Read the passages that support each rationale, and the store's own locators (`source_locator` on results and earlier use-case reviews).
3. Checked that each `method_ids` entry is the intended method or model record, and that the baseline configurations on the use case's active comparisons link to it by `configuration_of`, `family` or `variant_of`.
4. Rebuilt the same-data comparison table from `deriveUseCaseInputs` and configuration `facets.method_types`, using the website's rule from rewire-bio/rewire-database#185. A comparison is one presentation group, or one protocol if it has no group. A row is a baseline row when its configuration or its first `configuration_of`/`family`/`variant_of` target is in `method_ids`. A machine-learning row is any other row tagged `foundation_model` or `supervised_machine_learning`. `uses_model` links are not used, so the NeuSomatic ensembles that take Mutect2 and Strelka output are not marked as baselines.
5. Rewrote rationales that the sources do not support as worded, in plain text.

## Decisions on the open points

1. **Trained models as baselines.** Accepted where no pre-machine-learning method is measured and the trained model is the field's simplest established comparator: BayesDel, linear SVM and logistic regression, DeepSets, BLASSO, the GC and motif linear regression, and k-mer random forests. Each rationale says the model is trained. The patient-RNA legacy vote includes NNSplice, an early neural network, and its rationale says so.
2. **Baselines without a record.** Each is named by the closest existing record, and the rationale says what is missing: manual ENIGMA review (BayesDel), SURPI+ and CZ ID (Kraken2 and Centrifuge), BM25 (the ASCFDA team record, whose only configuration is its BM25 run), manual marker annotation (scmap-cell and linear classifiers), and the training-mean and composition controls (k-mer random forests). deFuse is not needed for the fusion baseline. No use case is left without a claim.
3. **Same-data comparison table.** Confirmed from `deriveUseCaseInputs` with the website's rule (see "How the check was done"). It matches the proposer's table, with two corrections. Model execution has no machine-learning comparison even after retagging. Fusion's only obstacle is the EricScript tag.
4. **Tag errors.** Listed below and not fixed here.
