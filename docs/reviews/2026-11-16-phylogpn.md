## All 124 values re-read, with controls

`data/omics/phylogpn-20261116/review/reread.py` was written for this pass. It does not import or run
`extract/parse_tables.py` and does not read `extract/tables.json`. It asserts the artifact hash,
parses the two `table-wrap` elements with `xml.etree`, keys every cell by its printed row label and
column header, and for each result checks:

- `printed_value` against the cell text and `numeric_value` against the cell with any asterisk removed;
- the metric concept against the column header's own parenthetical (`MCC`, `AUPRC`, `AUROC`) for
  Table 2, and against the Table 1 caption's "Each entry is an AUROC" for Table 1;
- `metric_direction` `higher`, `unit` `unitless`, and that `uncertainty` and `denominator` are
  recorded as unreported rather than given a value;
- that each `source_locator` resolves to exactly one cell, that no cell is claimed twice, and that
  every printed cell has exactly one result;
- the row-to-configuration assignment of each result's evaluation, against a mapping written
  independently from the paper (for the Expert Method row, against the parenthesised method name the
  table itself prints under each column).

All 124 pass: Table 1 is 12 rows by 5 columns with 60 printed values and 60 results, Table 2 is 10
rows by 7 columns with 64 printed values and 64 results. Output in `review/reread.txt`.

Because the source is JATS XML, column assignment is checkable directly, and it was: every one of the
124 locators resolves to the named row **and** the named column, and the five Table 1 column systems
and nine Table 2 row systems each match the configuration the paper's own text identifies.

**Negative controls** (`review/controls.py`, output in `review/controls.txt`). Each control mutates a
copy of `batch.jsonl` outside the batch folder and reruns the check. A clean copy passes; all four
mutations are caught and the mutated record is named:

| Control | Caught by |
| --- | --- |

| One result's column shifted by one (histone to CpG methylation) | cell claimed twice, value mismatch, and the vacated cell has no result |
| One result's row shifted by one (Missense to Noncoding) | value mismatch and the vacated cell has no result |

**`npm run batch -- check-values`** was rerun in this pass: 124 `in_cell`, and the `value-check.tsv`
it wrote is byte for byte the file the extractor left.

**Manual sample.** Ten rows, 70 cells, were read by eye in the raw `<tr>` markup
(`review/manual-sample.txt`): Table 1 rows `3’ UTR`, `Start Codon` and `Upstream of Transcript`;

**The six `N/A` cells are genuinely `N/A`.** Their `<td>` elements hold the literal string `N/A`,

The ten descriptive claims were re-read against the Methods, Results, Discussion, footnotes and

## Rulings

### 1. The two cross-source disagreements: one resolved, one withheld

`review/family-best.py` recomputed all 35 compiled Table 2 cells from the BEND results already in the
store (`review/family-best.txt`). The seven Expert Method cells match the stored Augustus, Enformer,
Basset and DeepSEA values exactly. Of the 28 family-best cells, 26 are the maximum of the stored
family values and two are not. Both are leads, and the printed values stand as printed.

**Nucleotide Transformer, Expression VEP, printed 0.54: resolved, no concern.** The deciding evidence
is the caption's own rule, "We report the best result among models in each family", read against
every subset of the family. BEND scored four Nucleotide Transformer models. Taking the best over
`{NT-MS, NT-V2}` or `{NT-MS, NT-1000G, NT-V2}` reproduces **all seven** printed cells of the row
exactly; every subset that includes NT-H, BEND's human-reference-only checkpoint, fails on this one
cell, because NT-H's stored Expression VEP value is 0.55 against NT-MS's 0.54. Seven cells out of
seven is not a coincidence: the family this paper applied the rule to does not include NT-H. That is
a difference in how the family is defined, not an error in the cell, so `source_discrepancy` stays
and now records the resolution, and no evidence concern was added.

**GENA-LM, Chromatin Accessibility, printed 0.84: not explained, so withheld.** BEND prints 0.76 for
GENA-LM BERT and 0.82 for GENA-LM BigBird. This review checked two renditions of BEND rather than
one: the ICLR 2024 proceedings PDF the store pins as `evidence-expansion-bend-final-f709b6be`, and the
arXiv rendition arXiv:2311.12570, retrieved 2026-11-16, SHA-256
`bfb40a6afe8028a52ea6c810bba3729510f1e768cc1288026b46e458df2d4ec9`, whose main results table prints
the same two values. The paper cites that version: reference 22 is "Marin F.I., Teufel F., Horlacher
M., Madsen D., Pultz D. et al.: BEND: Benchmarking DNA language models on biologically meaningful
tasks. In: The Twelfth International Conference on Learning Representations (2024),
https://openreview.net/forum?id=uKB4cFNQFg". So this is not a version difference. No subset of the
GENA-LM family reproduces all seven printed cells of the row, while DNABERT, HyenaDNA and Nucleotide
Transformer each have one that does. The printed value is therefore not the family best the paper says
it reports, and nothing published accounts for it.

Ruling: `source_discrepancy` alone is not enough here, because a reader comparing GENA-LM on BEND
chromatin accessibility would be comparing a number with no upstream. A scoped
`attributes.evidence_concerns` entry was added to `phylogpn-2025` naming exactly
`phylogpn-20261116-result-t2-chromatin-gena-lm`. The printed value is kept; that one result is
withheld from automatic comparison. The row's other six cells, the other 123 results and the source
as a citation are untouched.

**Is the comparison like for like?** Yes, and that is what makes both leads meaningful. Section 4.2
says of Table 2 "we reproduce results included in Marin et al. [22]", so these cells are that
paper's own numbers under BEND's own protocol, not a re-run: the evaluations carry origin
`paper_compilation` and a limitation saying the measurement is not this paper's. The stored BEND
results carry the same tasks (`bend-task-*`) and the same data subsets (`bend-dataset-*`), which the
batch reuses rather than duplicating, and both sides are AUROC, unitless, higher-is-better. What is
*not* like for like is the aggregation, and the batch already keeps that apart: each family-best
evaluation's `comparison.aggregation` is "Best result among the models of this family" and each
result's `metric_qualifier` ends with the same phrase, so a family-best cell cannot compare against a
single-model BEND result, which is right. The two leads are leads about the upstream values, not about
a mismatch of protocols.

### 2. Table 1 against Lu et al. 2025: a protocol difference the records already keep apart

Table 1 is higher than the stored `lu-hetero-20261019` PhyloGPN AUROCs on every overlapping variant
class, by 0.04 to 0.34. Nothing in the batch lets the two pool in a comparison, and that was checked
against the links rather than asserted:

- the two protocols are different records, `phylogpn-20261116-protocol-clinvar-llr-auroc` and
  `lu-hetero-20261019-protocol-clinvar-variant-type-auroc`, and neither links to a shared task or
  benchmark;
- all 60 Table 1 evaluations use the batch's own protocol and the batch's own 12 dataset subsets;
- no subset in the batch carries a `same_data_as` link to a Lu subset, and the two sets of subset IDs
  are disjoint;
- the `metric_qualifier` strings differ ("ClinVar pathogenic or likely pathogenic versus benign or
  likely benign, zero-shot allele log likelihood ratio, class 3’ UTR" against "ClinVar pathogenic vs
  benign SNVs, 3' UTR"), and a comparison requires the same qualifier as well as the same protocol,
  dataset, metric, unit, split and direction (docs/discrepancies.md).

The only thing the two share is the model: both sides' configurations resolve through
`configuration_of` to `lit-genomics-20261011-guanine-model-phylogpn`. That is correct and is how a
cross-study lead is meant to surface. The protocols differ in ways the paper itself prints: this paper
"included all variants that received at least one star and are labeled as pathogenic or likely
pathogenic in our positive class, and those that are labeled benign or likely benign in our negative
class", scored from "the probability of each state under the stationary distribution of the predicted
nucleotide substitution model", with no ClinVar release named; Lu et al. used `variant_summary`
2025-03-31 with MANE RefSeq v1.4, restricted to the variants every compared model scored, and ran
PhyloGPN from its official example code. The class definitions also differ: this paper's "Noncoding"
is not Lu's "Noncoding", as the 0.94 against 0.951 pairing shows against the much larger gaps
elsewhere.

Ruling: a protocol difference, already kept apart. The discrepancy rules cannot list this batch yet
because it is not in a release, so this is recorded pre-emptively: a future finding on a PhyloGPN
pair here will have scope `unknown` on both sides, since neither protocol is placed in a task, and is
a lead for curation rather than an error. No `discrepancy_review` claim was written, because there is
no current discrepancy ID to revise.

One defect was found while checking this and fixed in the batch. The new protocol has no
`evaluates_task`, `part_of` or `parent` link and had no `task_link_exemption`, so
`npm run check:task-links` would fail on it (`scripts/omics/check-task-links.ts`, the ratchet from
issue #208; the baseline list does not and must not grow). A `task_link_exemption` was added, with the
same reasoning as `lu-hetero-20261019-protocol-clinvar-variant-type-auroc` carries: the only candidate
anchors are the per-class legacy silos such as `reported-task-ed3dd3b83c4505`, which are
`needs_review` and whose own attributes say structured extraction is pending.

### 3. The duplicate source records: same bytes, duplicate retired

`phylogpn-2025` and `evidence-expansion-p2-phylogpn-2025-807f3a26cbfa` both carry `artifact_sha256`
`807f3a26cbfa9b5ce238d92164bd523302c67d1c5794b08273c51cca1acd4224` and the same Europe PMC
`fullTextXML` artifact URL. This review re-retrieved that URL and reproduced that hash, so the two
records pin the same bytes.

`companion_of` would be the wrong marker: the contract defines it as "a repository, leaderboard,
supplement or another version of a paper", and identical bytes are not another version. The relation
that fits is `supersedes`, which any kind may use.

Ruling, applied: `phylogpn-2025` gains a `supersedes` link to the duplicate and the duplicate's
status becomes `superseded`. `phylogpn-2025` is the record every result, evaluation and claim in the
store cites and the one the catalogue keeps under its original identifier, so it is the survivor even
though it was written two days earlier. Nothing is withdrawn: the duplicate supports no result, and
the only record citing it, the legacy task `reported-task-ed3dd3b83c4505`, cites `phylogpn-2025` as
well.

Left for the coordinator, deliberately: that legacy task still names the duplicate in `source_ids`
and in `attributes.benchmark_research.primary_sources`. Rewriting a `needs_review` silo record belongs
with the decision on the other three silo records behind `b2-phylogpn-2025` (ruling 5), not with this
batch.

### 4. The paywalled version of record, and the new publisher source record

The extractor's report that Europe PMC search fails for this paper is confirmed, and the resolution
is better than reported. `TITLE:"A Phylogenetic Approach to Genomic Language Modeling"`,
`DOI:"10.1007/978-3-031-90252-9_7"` and the bare quoted phrase each still return `hitCount: 0`. But
`PMCID:PMC11908359` returns one hit, and its core record carries PMID 40093357, the chapter DOI
`10.1007/978-3-031-90252-9_7`, the five authors and `license: "cc by-nc-nd"`. So Europe PMC holds the
identification; only its title and DOI search index misses it. Crossref gives the same chapter
(`book-chapter`, pages 99-117, published online 2025-04-25, Springer Nature Switzerland), and the
Springer page's citation metadata gives LNBI volume 15647 and first-online 25 April 2025. Three
independent routes agree, and none of them required the paywalled text.

Ruling: the publication identification holds. `phylogpn-20261116-source-springer-chapter` earns its
place, for one reason: `phylogpn-20261116-claim-version-of-record` cites it, and it is the only pinned
artifact in the store that carries the series volume, the page range and the first-online date. A
source that supplies no result value but is the pinned evidence for a claim is doing the job a source
record exists for. Its `limitations` already say no value in the batch comes from it, and its
`hash_scope` already says the hash describes one retrieval, which this review verified by getting a
different one.

### 6. Extractor questions 2 and 3: apply the two claims, keep `publication_status: preprint`

One rule decides both: does the field describe the artifact the record pins?

- `attributes.licence` = CC BY-NC-ND 4.0: yes. The pinned XML prints "This work is licensed under a
  Creative Commons Attribution-NonCommercial-NoDerivatives 4.0 International License", and Europe
  PMC's core record independently gives `cc by-nc-nd`. Applied; the `missing_metadata.licence` entry
  (`unextracted`) was removed with the fill.
- `attributes.version_note`: yes. It describes the artifact's relationship to the version of record
  without claiming to be it. Applied.
- `publication_status`: stays `preprint`. The artifact is the preprint, and a reader looking for the
  published version now finds it in `version_note`, in
  `phylogpn-20261116-claim-version-of-record`, and in the pinned Springer source record. Changing it to
  `peer_reviewed` would describe bytes the record does not hold.

Both claims move from `needs_review` to `source_checked`, and each change carries a
`metadata-correction-*` claim keeping the previous state.

`missing_metadata.doi` (`unextracted`) was left as it is, and this is a deliberate omission rather
than an oversight: the only DOI this work has is the chapter's, which identifies the version of
record, not the preprint this record pins. It is in `version_note` and on the Springer source record.

### 8. The remaining extractor questions

**Caduceus: two configurations, keep them.** The question is not whether the checkpoints are the same.
Appendix A.2 names `caduceus-ps_seqlen-131k_d_model-256_n_layer-16` for the likelihood-ratio
evaluation; Section 4.2 describes the Table 2 row only as "the largest RCE Caduceus model" and says
nothing more. Even if those were one checkpoint, the two evaluated setups are different: one is scored
by allele likelihood ratio, the other by a classifier on frozen embeddings. The store's practice is one
configuration per paper per evaluated setup, so merging them would be wrong either way. The
`model_identity_note` on the second record says exactly what the paper does and does not say, which is
the right amount of claim.

**DNABERT family-best: leave it with no `configuration_of` link.** The row genuinely mixes two family
records, and `review/family-best.py` proves it: the only subset of `{DNABERT, DNABERT-2}` that
reproduces all seven printed cells is both of them together. Gene Finding 0.43 is DNABERT-2's stored
value and DNABERT v1's is 0.20; Chromatin Accessibility 0.85 and Expression VEP 0.60 are DNABERT v1's
and DNABERT-2's are 0.81 and 0.49. Attaching the row to either family record would assign another
model's numbers to it. The consequence is that the row does not resolve to a model for the discrepancy
rules and so does not enter comparisons, which is the correct outcome for a two-family row. The
GENA-LM, HyenaDNA and Nucleotide Transformer rows keep their links, because BEND scored each of those
families' members under one family record.

**GUANinE: nothing to do, confirmed.** The string GUANinE occurs zero times in the pinned XML. The nine
stored GUANinE results for PhyloGPN come from the GUANinE benchmark paper and have no counterpart cell
here, so there is no disagreement to record. The consistency check the extractor noted holds and is
worth keeping: `lit-genomics-20261011-guanine-config-phylogpn-1pct` records a context column of "= 481",
and this paper's Methods state a 481 bp receptive field.

**Off-table prose values: correctly listed and not recorded.** The two Expression VEP likelihood-ratio
figures are printed where the extractor says and are quotable: "On this evaluation, PhyloGPN achieved
an AUROC of 0.55. By comparison, Nucleotide Transformer… achieved an AUROC of 0.36 on this evaluation."
So is the third: "we expanded the hidden size of the classifier to 32. In this case, PhyloGPN-X obtains
an AUPRC of 0.03." Each needs its own protocol record, because none shares the protocol of the table
row it sits beside. Listing them is the right call for a batch scoped to the headline tables.

**The `hg39` misprint.** Confirmed in the supplement, Appendix A.3: "since the MSA was constructed
using the hg39 human reference genome, we could only evaluate GPN-MSA on all BEND tasks except
Chromatin Accessibility, which is based on hg19 coordinates". No assembly called hg39 exists. Quoting
it in the GPN-MSA BEND configuration's limitations and inferring nothing from it is the right handling.
It does not affect any value: the sentence's operative content, which this review did rely on, is the
reason the Chromatin Accessibility cell is `N/A`.

**Table 1 GPN-MSA is `author_reported`.** Confirmed. Appendix A.2 ends "Lastly, we evaluated GPN-MSA
using pre-computed LLR values. These data are available at
https://huggingface.co/datasets/songlab/gpn-msa-hg38-scores." The authors ran the comparison on
published scores, which is what `author_reported` with a precomputed-scores configuration records.

## Gaps that remain

- **Version of record not read.** The chapter text is paywalled; `content/pdf/…` serves the same
  landing page. The preprint and the chapter were not compared, so a table that changed between them
  would not be visible. One read by anyone with institutional access settles it.
- **Table S1 (155 cells) and Table S2 (26 cells)** are deferred, not dropped; see ruling 7.
- **Figures 3a, 3b, 4, 5, 6 and S1 print no values** and were not read by eye. The OMIM regulatory
  comparison in Figure 3b has no printed numbers anywhere in the paper, so it is a true gap.
- **The GENA-LM chromatin cell's origin is unknown.** The concern withholds it; it is not resolved. An
  upstream question to the authors would settle it, and so would the version of record if the chapter
  prints 0.82.
- **No use-case judgements and no `coverage.json`.** The batch was scoped without them. The Table 1
  ClinVar likelihood-ratio protocol is a candidate for the variant interpretation use cases of issue
