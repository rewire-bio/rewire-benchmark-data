# Linked data

The canonical records can be read as RDF. Each release also produces a knowledge-graph bundle: the records as RDF, the facts that follow from the vocabulary (OWL 2 RL inference) in a separate graph, and the vocabulary itself. Claude and other MCP clients can query the bundle through [rdf-kg-mcp](https://github.com/rewire-bio/rdf-kg-mcp).

| File | Purpose |
| --- | --- |
| `data/ontology/mapping.json` | Maps each record kind to classes, each link relation to a property, and selected fields and attributes to properties. Each external term carries the reason it fits. Status: proposed. |
| `data/ontology/context.jsonld` | JSON-LD 1.1 context generated from the mapping. With it, every line of `data/entities/*.jsonl` and `data/evidence/*/*.jsonl` is a JSON-LD node. |
| `data/ontology/rb.ttl` | The rewire vocabulary: every `rb:` class and property, with labels, definitions and the axioms the build reasons over. |
| `data/ontology/imports/` | Pinned copies of ML Schema and DCAT, and extracted subsets of OBI, schema.org, SEPIO and ECO. `sources.json` records where each came from, its version, licence and checksum. |
| `data/ontology/shapes.ttl` | SHACL shapes the build validates against. |
| `data/ontology/discrepancy-rules.json` | Thresholds for the discrepancy rules ([Discrepancies](#discrepancies)). |
| `data/ontology/rb-attributes.ttl`, `data/ontology/attribute-shapes.ttl` | Generated by `npm run kg -- terms` from `shared/omics/attribute-registry.ts`: a property declaration for every declared attribute, and per-kind shapes giving each its datatype, node kind or concept scheme. |
| `data/vocab/<scheme>.ttl` | SKOS concept schemes for controlled fields: metrics (matched to STATO), units (QUDT), areas (EDAM), method types, contexts, publication status, origin, metric direction, entity level, baseline and configuration types, review methods, agents and record status; and the discrepancy rules and review states used by the derived graph. Records store concept keys. |
| `data/vocab/migration/` | The reviewed lookup from every former free-text value to its concepts, and per-record corrections. See [the 2026-10-09 review](reviews/2026-10-09-controlled-vocabularies.md). |

Identifiers are `https://benchmarks.rewire.it/id/<record id>`; the vocabulary is `https://benchmarks.rewire.it/vocab#`; concepts are `https://benchmarks.rewire.it/vocab/<scheme>/<key>`. A controlled field stores the key (`"metric": "auprc"`), and the JSON-LD context and the export expand it to the concept IRI, so each record line is linked data as stored. External terms come from W3C ML Schema (`mls:`), DCAT, Dublin Core, schema.org and OBI, only where their meaning matches; concepts match STATO, QUDT and EDAM. Everything else stays in the rewire vocabulary.

## Rules

- Record IDs and values are never changed by the projection. Every declared attribute is exported: under its property in the mapping when listed there, otherwise `rb:<camelCaseKey>`, typed by its registry type for the record's kind (`xsd:integer`, `xsd:decimal`, `xsd:date`, IRIs for URLs and record IDs, concept IRIs for controlled values, `rdf:JSON` for structured payloads). Uncertainty, coverage and reported population become nodes at `<record IRI>/<key>`; each missing reason becomes an `rb:MissingValue` node at `<record IRI>/missing/<field>` with its field and a `missingness` concept.
- `alias_of` maps to `rb:aliasOf`, not `owl:sameAs`, so a reasoner cannot merge records or their results without a review.
- Every relation has one meaning (`shared/omics/relations.ts`) and maps to one property. An evaluation links to what was actually evaluated through `system` (`rb:testedSystem`). `uses_model` (`rb:usesModel`) is not a subproperty of it and not transitive: a pipeline's result is never a result of a model it uses.
- Only public records are exported. Excluded, quarantined and private data never enter the graph.
- Mapping and vocabulary changes are reviewed like record changes. After editing `mapping.json`, run `npm run kg -- context` and commit the regenerated context.

## Inference

The build runs the OWL 2 RL rules over the asserted graph and the vocabulary, and keeps the new statements about records that are in the rewire vocabulary: `rb:` links and `rb:` types. Superclasses and superproperties from the imported vocabularies (such as `mls:InformationEntity` or `schema:Thing`) are not restated for every record; they follow from the ontology graph for any consumer that wants them. For the current release this adds about 103,000 statements to the 392,000 asserted ones.

| Inferred property | Meaning | From |
| --- | --- | --- |
| `rb:within`, `rb:contains` | Task or protocol inside a benchmark or suite, transitively, and the reverse | `rb:partOf`, `rb:parent` |
| `rb:resultFor`, `rb:resultOn`, `rb:resultOnDataset` | Result to the system, assessment and dataset of its evaluation | chains through `rb:evaluation` |
| `rb:testedWithin`, `rb:resultWithin` | Evaluation or result to every benchmark containing its task or protocol | chains through `rb:within` |
| `rb:hasResult`, `rb:testedIn` | The reverse of `rb:evaluation` and `rb:testedSystem` | inverses |
| `rdf:type` | `rb:System`, `rb:Assessment`, and `rb:Dataset` for subsets | the class hierarchy |

The build fails, and nothing is published, if:

- the reasoner finds an inconsistency, or a record is typed `owl:Nothing`;
- `owl:sameAs` is inferred between records;
- a protected link is inferred: `rb:evaluation`, `rb:testedSystem`, `rb:testedOn`, `rb:dataset`, `rb:family`, `rb:variantOf`, `rb:configurationOf`, `rb:aliasOf`, `rb:usesModel`, `rb:status` or `mls:hasValue`;
- a result's inferred `rb:resultFor` is not what its evaluation tested;
- SHACL validation fails. Among other checks, every evaluation has exactly one tested system, assessment and dataset, and every result exactly one evaluation, system, assessment and dataset.

`scripts/kg/tests` checks these rules on the vocabulary itself and on a small fixture, including a pipeline that uses a model and a configuration in a family, so a vocabulary change that would let results move between records fails the tests.

## Discrepancies

After inference, `scripts/kg/contradictions.py` looks for results from one study that disagree with results from other studies for the same systems, and writes each case to a separate derived graph as an `rb:Discrepancy`. OWL 2 RL cannot compare numbers, so this is a separate step, and its output is kept out of the inferred graph, which holds only what the vocabulary entails.

A discrepancy is a lead to investigate, not a finding that a result is wrong. It never changes a record's status, value or links; `check_derived` fails the build if it tries. The results stay on the site with a flag until a reviewer decides.

| Rule | Flags a study when |
| --- | --- |
| Ordering reversal | Other studies rank system A above system B in at least 5 comparisons, 80% of the time or more, and this study ranks B above A in at least 2 comparisons, 75% of the time or more. |
| Gap outlier | At least three studies compare A and B on the same protocol or task, and this study's median relative difference, (A - B) / B, is more than 0.10 outside the range of the others. Never above medium severity. |

Thresholds are in `data/ontology/discrepancy-rules.json`; the manifest records its checksum. How it counts:

- A comparison is two systems' best values in one group of one study's results: same protocol, dataset, metric, unit, qualifier, split and direction. Values within 1% are ties and do not count.
- Copied results (origin `paper_compilation`, or an `original_evaluation` link) are left out. Sources that share a result are one study.
- A configuration is compared as the model it configures (`configuration_of`, then `family`). Links without a checked claim are used, and the discrepancy is marked `rb:identityBasis "unreviewed"`. A configuration with no link is not compared, so linking comparators to their models is what lets the rules see them.
- Severity starts at high and drops a step each for comparisons on different tasks (`cross-task`), unreviewed identity links, and the gap rule.

The terms reuse existing ontologies where they fit. `rb:Discrepancy` is a SEPIO assertion (SEPIO_0000001). The results and sources it rests on are linked through subproperties of SEPIO `has_supporting_evidence` and `has_supporting_evidence_from_source`. `rb:assertionMethod` is ECO `automatic assertion` (ECO_0000203) until a reviewer decides, then `manual assertion` (ECO_0000218). The rule concepts match STATO `ranking` and `relative difference`. CiTO's `disagrees with` was not used, because it states a citing paper's intent, and the studies in a discrepancy rarely cite each other.

### Recording what was done about one

A discrepancy is rarely settled in one step: you investigate, raise it with the authors, and wait for a correction. A claim with `field` `discrepancy_review` records both where it stands and the work behind it. Set `discrepancy_id` to the discrepancy's ID (`discrepancy-<hash>`, stable while its rule, systems and outlier study stay the same), `value` to a state from `data/vocab/discrepancy-state.ttl`, and subject links to the results involved.

The states are `open` (rule output, nobody has looked), then `investigating`, `reported-upstream` and `awaiting-correction` while the work is going on, then `explained`, `confirmed-error` or `false-positive`, which settle it. Only the last three clear the flag on the site; the working states show the discrepancy as being handled, with its latest step.

| Attribute | Holds |
| --- | --- |
| `investigation_url` | Our own analysis: an issue, a dated review |
| `report_url`, `reported_on` | What we raised with the authors, and when |
| `upstream_response` | What they said, and when |
| `awaiting`, `expected_by` | What has to happen next, and when they said it would |
| `next_check` | When to chase it |
| `resolved_by` | The corrected source or superseding results, once they exist |
| `rationale` | Why the state is what it is |

A later step is a new claim with a higher `revision`; the highest revision is the current state, and the earlier claims stay as history. `next_check` is published as a date, not an overdue flag, so the same release always produces the same bytes; the website and the monthly refresh decide what counts as overdue when they read it. A confirmed error is then fixed through a normal reviewed record change, which is what marks the affected results `disputed`.

### For the website

The serving database is built in the data release, before the knowledge-graph bundle, so discrepancies are not in it. `kg:publish` uploads `discrepancies.json` to the `kg/<release id>` release beside the bundle and its manifest: `https://github.com/rewire-bio/rewire-benchmark-data/releases/download/kg/<release id>/discrepancies.json`. The manifest's `derived.discrepancies_json_sha256` is its checksum. The file holds `release_id`, the `rules` in force and a `discrepancies` list; each entry carries `rule`, `summary`, `severity`, `scope`, `identity_basis`, `review_state`, `settled`, `resolution`, the compared `systems`, and the `outlier_results` and `consensus_results` it rests on. A results page flags a result listed in `outlier_results` of an unsettled discrepancy. Bundles published before discrepancies existed have no such file, and a reader treats that as no discrepancies.

## Commands

```sh
npm run kg -- context   # regenerate data/ontology/context.jsonld from the mapping
npm run kg -- export    # write public/kg/asserted.nq and an export manifest
npm run kg -- terms     # regenerate rb-attributes.ttl and attribute-shapes.ttl from the attribute registry
npm run kg -- subset <ids-file> <dir>  # the given records, the records linking to them and their link targets
npm run kg:shapes       # export, then SHACL on the asserted graph without inference (a few minutes)
npm run kg:build        # inference, checks, SHACL and discrepancies; writes inferred.nq, derived.nq, discrepancies.json, ontology/ and the bundle manifest
npm run kg:bundle       # export, then kg:build: the whole bundle for the current release
npm run test:kg         # vocabulary and inference tests
```

`npm run build` does not build the knowledge graph; run `npm run kg:bundle` after it. The KG build needs [uv](https://docs.astral.sh/uv/), which installs the pinned Python dependencies in `scripts/kg/requirements.txt`. It takes about two minutes locally and 1.5 GB of memory. `kg:shapes` skips property shapes on links only the reasoner creates (property chains and inverses); it runs on every pull request. `records -- add` and `records -- change` run the same shapes on a subset: the records they wrote, the records that link to them, and the records those link to. Violations on the last group are ignored, because their own links lead outside the subset. The output is sorted and deterministic: the same release, mapping and vocabulary give byte-identical files.

To update a pinned vocabulary, download it, re-run the extraction command in `data/ontology/imports/sources.json` where one is listed, update the checksum there, and review the change in the inferred graph.

## Bundle

`public/kg/` holds a bundle in [rdf-kg-mcp format 1.0](https://github.com/rewire-bio/rdf-kg-mcp/blob/main/docs/bundle-format.md):

| Path | Graph | Contents |
| --- | --- | --- |
| `asserted.nq` | `https://benchmarks.rewire.it/graph/asserted` | The public records |
| `inferred.nq` | `https://benchmarks.rewire.it/graph/inferred` | Inferred statements about records |
| `derived.nq` | `https://benchmarks.rewire.it/graph/derived` | Discrepancies between studies |
| `ontology/` | `https://benchmarks.rewire.it/graph/ontology` | `rb.ttl`, the pinned imports and the concept schemes (`ontology/vocab/`) |
| `manifest.json` | | Checksums, counts, graph roles, prefixes, reasoner and SHACL details, example queries |

Bundles are built after each data release, in their own workflow, "Build and publish a knowledge-graph bundle" (`.github/workflows/kg-release.yml`), which the release workflow starts once the release is published; it can also be run by hand for any published release ([release.md](release.md#knowledge-graph)). It runs `npm run kg:publish`, which packs a byte-reproducible `kg-<release id>.tar.gz` and publishes it with the manifest on a GitHub release tagged `kg/<release id>`. An existing asset must be byte-identical and is never replaced (`npm run kg:publish -- --check` verifies it).

The simplest way to use it is the `bio-model-benchmarks` plugin for Claude Code, which installs the knowledge-graph server and a skill for running the benchmarks; setup for other agents is at [benchmarks.rewirebio.io/agents/](https://benchmarks.rewirebio.io/agents/). To add only the server:

```sh
claude mcp add rewire-benchmark-graph -- uvx --from git+https://github.com/rewire-bio/rdf-kg-mcp@v0.1.0 \
  rdf-kg-mcp serve https://benchmarks.rewirebio.io/agents/kg.tar.gz
```

`https://benchmarks.rewirebio.io/agents/kg.tar.gz` redirects to the bundle of the release the website serves. That bundle is published a few minutes after the release, so a client that starts in that window should retry. For an exact reproduction, serve one release's bundle: `https://github.com/rewire-bio/rewire-benchmark-data/releases/download/kg/<release id>/kg-<release id>.tar.gz`.

Or serve a local build with `rdf-kg-mcp serve public/kg`.
