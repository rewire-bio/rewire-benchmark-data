Architecture decision record 0004 · rewire-benchmark-data

Storage substrate and repository weight

Proposed Proposed 2026-11-17 Decider Tim Richardson, not yet ruled Measured at 991a09ef on origin/main
Answers the owner's two questions: should the store move off git, and can every original source be kept Related #228 (staged extraction), which reads archived source bytes

The repository looks bloated, so the question was whether to move the record store to a warehouse or an object store. The store is not the weight. It is 17,241,502 bytes of the 282,381,286 bytes of tip blobs a fresh clone fetches, 6.1 percent. The weight is 34 binary files. This record keeps git canonical, evicts those binaries to a content-addressed archive, and gates what enters. It is not accepted: five questions below need the owner's ruling first.

Problem

A fresh blobless clone costs 269.55 MiB of .git. Binary files are 90.8 percent of live history disk. A history rewrite cannot move GitHub's reported 3.01 GB, because refs/pull/* keeps the old commits reachable and is read-only to us.

Decision

Git stays canonical and no history is rewritten. The 34 tip files over 1 MiB move to a content-addressed archive on GitHub release assets, and a content gate stops new source bytes entering git. Parquet is a derived export; no warehouse is built.

Expected effect

A fresh blobless clone drops from 269.55 MiB to about 54 MiB of .git. The gate is worth about 2.7 GB of clone cost per contributor over five years. No tag, pin, release ID or provenance hash changes.

Context

The repository is public, holds 93,187 curated records, and is maintained by two people. The owner asked two things. First, whether to move off git, because the repository looks bloated. Second, that every original source be stored, so that a later reader can reproduce what an extraction read. Both are answered here from measurement, not from a size feeling.

Three independent designs were written and scored. Where they disagreed, the disagreement is settled below by a fact and the losing figure is named, not quietly dropped.

A blobless clone never fetches history blobs. Its .git is 1.2 MB before checkout and grows only by the blobs the checkout needs. So the whole of the repository's history is already free to a contributor who clones this way, and the only thing a fresh clone pays for is the tip tree.

One earlier reader could not measure this and estimated roughly 270 MB from rev-list --disk-usage plus the depth-1 pack, because the local file:// transport answers "filtering not recognized by server" and silently gives a full clone. The clone above was made against GitHub, so the estimate is now a measurement and the two agree.

The canonical store is 6.1 percent of that. In the working tree it is 241,215,685 bytes of JSONL over 93,187 records, and git delta-compresses it to 17,241,502 bytes of pack disk. Moving it to any other substrate removes 16.4 MiB from a 269.3 MiB checkout and leaves the other 93.9 percent exactly where it is.

The two numbers 269.3 MiB and 269.55 MiB are different quantities that happen to be close: the first is tip blob disk, the second is the whole .git of the blobless clone, which also holds every commit and tree. They are not rounded into each other anywhere in this record.

335 incompressible tip files (gzip, pdf, zip) hold 245,707,448 bytes, 234.3 MiB, of the total. 34 of them are over 1 MiB and hold 226,382,825 bytes, 215.9 MiB, on their own.

Options weighed

ABigQuery or a lakehouse as the canonical storeRejected

Pros

  • SQL over the whole store makes each normalisation defect class one query: unit against metric, direction against the metric default, duplicate tuples, printed against numeric value. Today each needs a 382 MB SQLite build or a walk over 241,215,685 bytes of JSONL.
  • IAM can make an extracting agent unable to write the store. Git cannot.
  • Table clones are delta-billed, so per-pull-request validation is affordable.
  • Cost is about zero at this size: 0.225 GiB scanned by 14 jobs over 126 pushes a month is 0.387 TiB against a 1 TiB free tier.

Cons

  • The JSON type normalises object keys, which invalidates all 93,187 provenance hashes. The verbatim line has to be a raw STRING column, at which point the warehouse is a blob store with SQL beside it.
  • No reviewable line diff. Recent evidence pull requests are 64 to 356 files and up to 63,417 lines, and the diff is the review.
  • Every local build would need credentials, against a documented posture of fetching over anonymous HTTPS.
  • Time travel caps at 7 days plus a 7 day unqueryable fail-safe, against unbounded git history.
  • 22 files import records.ts and six in-place migration scripts would need SQL rewrites, against a store where 44.9 percent of records have already been mutated.
  • It removes 16.4 MiB from a 269.3 MiB clone.

Rejected on mechanism and on the measurement, not on price.

BRewrite history now with git filter-repo, removing the 2.43 GiB of dead release bundlesRejected

Pros

  • Removes 74.5 percent of reachable history, 2.431 GiB over 1,298 blobs.
  • The bundles are already gitignored and nothing in the build reads them from the tree.

Cons

  • It saves a fresh contributor zero bytes. A blobless clone's .git is 1.2 MB before checkout and never fetches history blobs.
  • It cannot be relied on to reduce GitHub's reported size either, for the reason in the figure above.
  • 148 tags change target, with an undocumented effect on the Release objects holding the published assets. 57 of those tags are the only public source of their release files.
  • A private repository's pinned commit SHA breaks, and release-config.json's source_revision goes missing, after which changelog.mjs:27-29 returns null and silently empties the release notes.
  • 90 open branches rebase.
  • 15 commit SHAs cited in review receipts stop resolving. That rewrites pins, which this project's own rules forbid doing by hand.

On the size claim: a post-rewrite plain clone is not 0.9 GiB. That figure subtracts 2.43 GiB from the 3.27 GiB reachable in the source repository, not from the 2.80 GiB a fresh plain clone actually costs. Since gzip does not delta in either, the honest figure is about 0.4 GiB, and it is worth nothing to a contributor who clones blobless.

CKeep git canonical, evict binaries to a content-addressed archive, gate what entersChosen

Pros

  • Every invariant above survives untouched. No record, field, ID, release ID or provenance hash changes.
  • The clone saving is the largest available and it is measured: 269.55 MiB of .git to about 54 MiB after the 34 files over 1 MiB leave, and about 35 MiB if the whole incompressible set follows.
  • The archive reuses expand() and safePath() from scripts/release/files.ts, the code already carrying the current release's 894,198,579 expanded bytes across 35 files in production.
  • It is the same mechanism the source-preservation ask needs, so one layer serves both.
  • Zero money, no new service, no new vendor, no new secret.

Cons

  • GitHub's reported 3.01 GB stays 3.01 GB.
  • The archive becomes a dependency of reproducing a pre-2026-10-14 release, which is a single point of failure that does not exist today.
  • The dominant cost is licence triage, not engineering. Licence is absent on 1,075 of 1,483 sources and nothing may be archived until that is resolved.

DOption C plus a frozen-batch retention policyDeferred

Rejected as a day-one control, on the measurement in the first figure. Batch intake text is 18,777,335 bytes of pack disk across all history. A 90 day freeze and thaw cycle would shrink the working tree, which is 745 MB under data/ today, 509 MB of it data/omics, growing at roughly 2 MB a day, but it adds a thaw step for every reviewer reopening an old batch and it bounds the cheap 7 percent. Kept as a named lever with a numeric trigger: pull it when a blobless checkout passes 2.5 GB in total.

EOption C plus a BigQuery mirror and dbt models on day oneRejected

Rejected on maintenance and drift. A mirror invites people to quote the mirror, and the design that proposed it says so itself. It adds a Workload Identity Federation binding (the existing trust is specific to rewire-database, so extending it is a new binding, not a reuse), a dbt project whose flattening models must track shared/omics/attribute-registry.ts by hand, and a second place where defect checks live. The useful part, deterministic SQL over the store, is available with no cloud at all through Parquet plus a local DuckDB file, and that is what is adopted.

Decision

  1. The canonical store stays data/{entities,evidence,provenance}/*.jsonl in git, unchanged. No field moves, no hash changes, no release ID changes, no credential on the build path.
  2. No history rewrite, and no size trigger for one. tools/repo-weight.mjs prints gh repo view --json diskUsage on every run so the number is in the logs, but it is a dashboard and not a trigger, because a rewrite cannot be relied on to move it. The only trigger left is legal. If a rewrite ever happens, its preconditions are: the 57 tags' files are already archive objects and the raw.githubusercontent.com fallback is deleted; the 15 cited commit SHAs have been migrated to release IDs; source_revision fails loudly instead of returning null; and the tag force-update behaviour has been settled on a scratch repository rather than guessed.
  3. git gc on the owner's clone reclaims about 2.06 GiB of the 5.33 GiB .git/objects that is unreachable or duplicated across two packs. Use plain git gc with its default two week prune window while about 30 agent worktrees share one object store. Use --prune=now only with no other session active.
  4. The blobless clone becomes the documented clone, with a code-only sparse profile beside it. Both are measured in the table above.
  5. A content-addressed blob archive is the new layer. The key is the sha256 of the expanded original bytes, which is exactly attributes.artifact_sha256 as the records already define it. Objects are stored gzipped and verified on expanded bytes with the existing expand(). The public backend is GitHub release assets on tags archive/objects-<first hex digit>, so the tag shard aligns with the manifest shard and a reader finds the tag from the hash with no lookup. The manifest is committed at data/archive/objects/<0-f>.jsonl, sorted by sha256, one line per object, with store and visibility as enums so a second backend is a config value and not a redesign.
  6. layer is a first-class field, not a caveat in prose. Three downloads of the GPN-MSA preprint, all 2,247,726 bytes, gave two distinct container hashes, neither of them the pinned one, while the pdftotext -layout text layer was identical at c6e95eb8... across all three and no record holds it. An object carries layer from exact-bytes, archive-member, text-layer, canonical-json; when the layer is not exact-bytes it must also carry derived_from (the container digest) and derivation (the exact command). A failed pin is recorded in superseded_pins beside the new observation and never replaced, which is what the rfd4-proteina review requires.
  7. Eviction is content-based, at a 1 MiB threshold. The gate is: no tracked file whose sha256 appears in data/archive/objects/*.jsonl; git ls-files -ci --exclude-standard must be empty, which closes the hole that produced 2.43 GiB without a hand-maintained path list; the existing 50 MB per-file ceiling stays; and tracked bytes under data/ stay under a committed ceiling in docs/repo-weight-budget.json. A path glob is the wrong tool: 65.6 MiB of pdf.gz sits under data/omics/reviewed/ with no artifacts/ segment in the path.
  8. Parquet is added as a derived per-release asset, and no warehouse is built. The export carries the verbatim JSONL line as a column and is written by TypeScript so JSON.stringify matches. Its acceptance test is that re-emitted JSONL reproduces the store digests through the same storeDigests(). Byte identity of the Parquet itself is not claimed, because pyarrow stamps its version into the footer's created_by and that field is not settable through the API. The near-term consumer is our own deterministic defect checks, run against a local DuckDB file with no cloud account and no language model. BigQuery stays a 30 line loader against the same files, unbuilt until a named consumer asks.
  9. Three breakpoints are named and deferred, each to its own decision. The prepared SQLite file passes GitHub's 2 GiB asset cap at about 484,500 records, which is the first thing that actually breaks and has nothing to do with the canonical store. The knowledge-graph build takes 693 s for 2,271,639 asserted and 282,012 inferred statements inside an 80 minute job, and owlrl rule joins are superlinear. The largest results shard is 7.34 MB against the 50 MB gate, fixed by one records -- reshard command, which does not change release IDs.

Implementation sequence

Step 1 is the first pull request. It proves the substrate on 2.43 GiB of our own build output, with no licence triage, no record schema change and no byte leaving the tip tree. Steps 3 and 5 can run in parallel after it.

1

Archive substrate, backfill, weight gate

  • scripts/archive/{objects,manifest,cli,backfill}.ts, reusing expand() and safePath().
  • Upload the 57 pre-2026-10-14 tags' release files, deduped by content, to the archive/objects-<x> tags; write the 16 manifest shards.
  • fetchRelease resolves through the manifest by the receipt's sha256; delete the raw.githubusercontent.com branch.
  • tools/repo-weight.mjs, docs/repo-weight-budget.json, tools/clone.sh, one step in the store job.
2 days of code plus about an hour of upload. Removes a standing single point of failure.
2

Evict the 34 tip files over 1 MiB

  • Audit the 52 artifact_url values that point into this repository for branch pins against commit pins; record previous_path in every manifest line.
  • Make auditInputFiles() throw, with a test.
  • Add the objects, add the gitignore entries, git rm --cached, switch the content gate on.
1 day plus a careful release rebuild. Blocked by step 1.
3

Typed source fields, second identity

  • Additive registry entries with the layer, store and visibility SKOS schemes, plus superseded_pins.
  • One fetcher that records what none records today: HTTP status, final URL after redirects, ETag, Last-Modified, response Content-Type.
  • An archive pass in records -- check, warning only, and warn-only on fork pull requests, which have no credential.
3 days. Zero existing records change. Blocked by step 1.
4

Licence resolution, then the cited-source archive

  • Resolve licence for the 1,075 sources that lack one from Crossref, Europe PMC and repository LICENSE files, as a correction set for apply-corrections.ts.
  • Archive the 574 cited-but-unstored sources in descending citation order, licence resolved per source as a gate on each upload. licence_class defaults to restricted, never open.
Weeks, almost all of it licence resolution. Blocked by step 3.
5

Parquet export, local DuckDB, four checks

  • Export carries the verbatim line; published as extra assets of the existing serving/<id> tag.
  • The round trip is the acceptance test. The receipt records the writer identity and the footer created_by.
  • Four deterministic store-convention checks, reporting counts without failing the build until they clear a flag ceiling and a false-positive ceiling.
2 days for the round trip, 3 for the checks and their pilot. Blocked by step 1.
6

Scheduled refetch

  • Weekly cron re-downloads a sample, records both identities and the response metadata, and writes a finding when the container hash moved but the text layer did not, or when both moved.
  • Nothing is corrected and no pin is ever rewritten.
1 day. This is what makes a pin checkable at all. Blocked by step 3.
7

Deferred, each with a numeric trigger

  • Serving contract 4.0 splits the prepared file by the existing shardOf(id); trigger is the single file passing 1 GiB, about 230,000 records, or its build passing 600 s against 184 s today.
  • Frozen-batch retention; trigger is a blobless checkout total passing 2.5 GB.
  • Reshard to 256 shards; trigger is the largest results shard passing 25 MB, currently 7.34 MB.
  • Move the knowledge-graph build out of the 80 minute release job; trigger is that step passing 40 min, currently 693 s.
Each trigger is a line in docs/repo-weight-budget.json or docs/serving-contract.md, printed on every CI run, so the threshold is in the logs and not in someone's memory.

Money

Zero a month in the recommended branch. GitHub release assets are free, with 1,000 assets per release, 2 GiB per file, and no documented total size or bandwidth limit.

Git LFS is rejected: 0.07 dollars a GiB of storage plus 0.0875 a GiB of transfer, fork and Actions downloads count against the parent repository, and GitHub's own documentation says removed objects keep counting against quota with repository deletion as the remedy. Cloudflare R2, if it is ever chosen for restricted bytes, is 0.015 dollars a GB-month with free egress, so about 0.05 dollars a month at 3 GB. One Zenodo deposit a year of a tar of the open objects, for a DOI and an off-GitHub copy, is free.

Costs that are real

Licence triage is the dominant cost of the source-preservation ask and no design makes it cheaper. Licence is absent on 1,075 of 1,483 sources, 16 state in prose that no copy is archived, and 45.2 percent of evidence citations (47,081 of 104,243) rest on a source whose bytes are not stored. Resolved against Crossref, Europe PMC and repository LICENSE files it is about two days of scripting plus a review pass per batch; by hand at two minutes a source it is 36 hours.

Maintenance for two people, for as long as the project runs: one manifest to keep sorted, enforced by CI. One archive -- add step in the acquisition procedure, which also records the source-to-file join the operator loses today, because batch.py:426-445 takes it on the command line and then writes two unjoinable dicts into review.json. One budget line to raise deliberately. One extra shard tag when a shard approaches GitHub's 1,000-asset cap. One weekly refetch cron whose output is findings a human reads. One git gc a quarter.

Risks

  1. The archive becomes a dependency of reproducing the 57 pre-2026-10-14 releases once the raw.githubusercontent.com fallback is deleted. Mitigated by not rewriting history, so git stays the cold copy, plus one Zenodo deposit a year. It is still a new single point of failure.
  2. Evicting data/omics/audits is safe for current releases, because release.ts:157 gates loadAudits() on extraCoverage.audit_history, which only the two 2026-09-20 receipts set. But auditInputFiles() returns [] when the directory is absent, so regenerating a September release after eviction would silently emit an empty audit index. Step 2 makes it throw. Missing that fix produces exactly the silent-wrong-output defect this repository's own reviews call class 10.
  3. Gitignoring artifact paths breaks joins that are not fully audited: 52 artifact_url values point into this repository, and every batch review.json keys its files dict by relative path. Step 2 checks each of the 52 for a branch pin rather than a commit pin, and records previous_path in every manifest line before any removal.
  4. The 8 CC BY-NC-ND and 1 CC BY-NC source artifacts already committed in this public repository are current exposure, and a rewrite cannot remove them from GitHub. This decision does not fix that. It is owner question 4.
  5. Growth is lumpy. One pull request added 63,417 lines. Every five-year figure here rests on a 33 day window on a project a few months old and could be 2x off either way. The conclusion survives a 2x error in the recommended branch.
  6. The content-based gate is a stat and hash walk over tracked files. At 3,146 files it is seconds. At 20,000 it needs a cache keyed on the git index.

Open questions for the owner

This record is proposed, not accepted. Five questions are the owner's to rule on. Step 1 does not depend on any of them, so it can ship while they are open.

1. Which backend holds restricted bytes, when licence triage produces the first object that needs one

Note first that this is not free in either branch. Every gh call in CI uses ${{ github.token }}, which is repository-scoped, so reading a private sibling repository's release assets needs a new PAT or GitHub App exactly as an object store needs a token.

  • (a) Release assets on a private rewire-bio repository: zero money, one new GitHub secret, no new vendor, no off-GitHub copy.
  • (b) Cloudflare R2: 0.015 dollars a GB-month with free egress, about 0.05 dollars a month at 3 GB, one new scoped token, an off-GitHub copy, and signed time-limited URLs for third parties.
  • (c) Store no restricted bytes at all, recording only the pinned hash and the normalised text layer.

No default. The manifest's store and visibility enums make this a config value in every branch, so the cost of deferring is zero.

2. How hash_scope is migrated

587 records carry one of 106 free-text values and 868 records have an artifact_sha256 with no scope at all.

  • (a) Add archive_layer as a new SKOS-backed enum beside the free text, rewriting zero records, zero provenance hashes and no release ID; the free-text values stay exactly as written and new records carry the enum.
  • (b) Classify all 587 through records -- change with a docs/reviews entry, which rewrites 587 provenance hashes by the sanctioned path and changes the next release ID, giving one clean field at the cost of a large reviewed migration.

Default: (a).

3. How far licence triage runs before anything is archived

Licence is absent on 1,075 of 1,483 sources, and this is the only thing blocking the source-preservation ask.

  • (a) Resolve all 1,075 before archiving any source byte: about two days of scripting plus a review pass per batch, or 36 hours by hand, and the archive waits weeks.
  • (b) Archive only the 408 sources that already record a licence, which leaves most of the 45.2 percent of evidence citations that rest on unstored bytes still unstored.
  • (c) Work in descending citation order and resolve licence per source as a gate on each individual upload, so the 574 cited-but-unstored sources clear in the order they matter.

Default: (c).

4. What to do about the 9 non-commercial artifacts already public

8 CC BY-NC-ND and 1 CC BY-NC source artifacts are committed in this public repository, for example data/omics/gpn-paper-20261116/artifacts/pnas-2311219120-si-appendix.pdf.gz. A history rewrite cannot remove them from GitHub, because refs/pull/* keeps the pre-rewrite commits reachable and is not force-pushable.

  • (a) Leave them, record the exposure as a finding in docs/, and apply the licence_class default of restricted to everything new.
  • (b) Open a GitHub Support request to dereference the affected pull requests and clear cached views, accepting that the documented policy is that Support will not act for non-sensitive data.
  • (c) Remove them from the tip tree in step 2, which cuts clone cost and future exposure but does not remove them from history.

No default. This is a legal question, not a size question, and it should not be inferred from a storage decision.

5. Whether to pre-agree the serving contract 4.0 lock bump now

The prepared SQLite file is 382,124,032 bytes uploaded raw, so GitHub's 2 GiB per-asset cap binds at about 484,500 records. The split needs serving.files[] in place of serving.file in the private rewire-database repository's benchmark-data.lock.json.

  • (a) Agree the lock-bump protocol with the website repository now, while it is cheap and nobody is under pressure, and ship the split on its trigger.
  • (b) Wait until the trigger fires and negotiate the cross-repository change then.

Default: (a). It costs an afternoon of agreement and removes the only cross-repository dependency on the critical path.

Considered and rejected, and why

A rewrite takes GitHub diskUsage from 3.01 GB to about 0.5 GB, so "diskUsage above 4.5 GB" is the trigger to reopen this decision. GitHub documents that rewritten commits stay reachable through any pull request that references them and in cached views, that only Support can dereference those, and that Support will not act for non-sensitive data. Verified in the repository: all 57 Cut release commits are single-parent direct pushes, and every pull request opened since, including #248 on 2026-11-15, has them as ancestors. The trigger is removed. It was a trigger on a number the proposed action cannot move. The only rewrite trigger left is legal.
76 to 80 percent of data/omics growth is batch text, so a frozen-batch retention policy is the growth bound and archiving binaries "shaves about a fifth off the curve". Pack disk, not apparent bytes, over all 4,074 omics blobs reachable from origin/main: intake text costs 18,777,335 bytes of disk from 312.2 MiB of content, against 229.5 MiB of live binary. Binary is 90.8 percent. Content eviction of binaries is the day-one control. Retention becomes a working-tree lever with its own trigger.
The canonical store costs about 0.15 GB server side across all history. That figure is a residual forced to GitHub's 3.01 GB, not a measurement. An independent reader measures the store's whole history at about 0.39 GiB, and the tip is 17,241,502 bytes of blob disk, 6.1 percent of 282,381,286, reproduced to the byte by aggregating git cat-file --batch-check='%(objectsize:disk)' over the tip tree. The conclusion the two shared, that the store is not the weight, survives either way, but the measured number is the one this record uses.
A private sibling repository for restricted bytes costs "no new vendor, no new secret, $0" using the GITHUB_TOKEN CI already holds, which is the deciding advantage over an object store. Every gh invocation in .github/workflows/*.yml uses ${{ github.token }}, scoped to the running repository, and the single separate secret is secrets.WEBSITE_DISPATCH_TOKEN. Reading another private repository's release assets needs a new PAT or GitHub App. Both options cost one new secret, so the choice is made on price, durability and whether an off-GitHub copy is wanted. That is why it is owner question 1 and not a decision here.
A nine-column Parquet schema with attributes re-serialised as a JSON string gives a reproducible export. That schema cannot carry the verbatim line, so storeDigests() cannot be reproduced from it and no determinism claim stands. A raw line column can, and the writer must be TypeScript, because Python json.dumps does not match JSON.stringify on floats and separators. The line-carrying schema with a TypeScript writer is adopted, with the store-digest round trip as the acceptance test.

Where issue #228 is wrong

#228 proposes the staged, source-grounded extraction pipeline that will re-read archived source bytes, so this archive is one of its build inputs. It states as a decision driver that "Sources under CC BY-NC-ND are hashed, not stored".

That is the intended rule and it is not what the repository does. Classifying licence over all 1,483 source records finds 80 CC BY-NC-ND and 19 CC BY-NC, and 8 of the CC BY-NC-ND plus 1 of the CC BY-NC have their original bytes committed in this public repository. Nothing enforces the rule: no build step reads an artifact byte at all, the only source check is shared/omics/validation.ts:81, which asks for a URL and a retrieval date, and records -- check contains no occurrence of "artifact". Read #228's line as a requirement this decision has to implement, not as a description of the current state. Decision 5 and the licence_class default of restricted are what make the rule true going forward; the nine already public are owner question 4.

Other things weighed and not taken

  • Git LFS. Priced above and rejected on quota mechanics, not only on price: fork and Actions downloads count against this repository, and removed objects keep counting.
  • Iceberg, Delta Lake, lakeFS. An operating surface for two people, at 230 MiB of text with one writer.
  • Content-defined chunking in the style of the Hugging Face Xet migration. It is the right answer for a hub serving 20 PB over many writers. Here the incompressible set is 34 files and the eviction gate costs nothing to run.
  • Shallow clones as the documented recipe. CI is already shallow or blobless: release.yml:47-48 passes filter: blob:none and the 14 checks jobs run at depth 1. The gap was the contributor recipe, which decision 4 closes.
  • A per-artifact Zenodo deposit. Zenodo caps at 100 files per record, against roughly 1,500 artifacts. One deposit a year of a tar of the open objects is the useful form.
