Claim and value extraction

Proposed Date 2026-11-17 Decider Tim Richardson Proposed 2026-11-17, two open questions below
Answers #228 Store measured 52,278 results, 24,726 evaluations, 4,155 claims, 1,483 sources, 93,187 provenance lines, at 991a09e
Related records 0003 decides how source bytes are captured, identified by two hashes and tiered by licence, and it captures the layers this record addresses; 0004 decides the storage substrate, and its object store holds those layer bytes; 0005 decides how a model or benchmark carries a runnable how-to

A stored value is checked for shape and for provenance-hash integrity. Nothing checks that it means what the source says, and nothing binds it to a place in the source that a second reader can find. This record decides what to build: deterministic checks first, over a locator that carries byte spans into a pinned text layer, with a language model at exactly one place in the pipeline and its output admitted only on a byte-span match.

Problem

In the 2026-11-15/16 pass, 13 of 13 batches needed a correction and the deterministic value check caught none of them. The one locator grammar parses 39.3% of stored locators and has been run on 14 of 194 batch folders.

Decision

A layer registry over the hashed derived text, a key-value locator grammar authored structured and rendered to the printed string, fifteen model-free checks that ship as a report with a ratchet, one model stage group behind a span check.

Status

Proposed. The first PR is report only and writes nothing to the store, and its ratchet is already shipped. Two questions below need the owner's ruling before the gates can land; a third, where layer bytes live, is answered by ADR 0004.

Context

A source becomes records through four stages that are only partly shared: pin and hash the artifact, parse it into cells, render cells into record JSONL, verify and load. Only the TypeScript lane ever had a shared claim shape and a shared record renderer. It has been dead since 2026-10-09 17:13, when scripts/omics/extract/batch.ts was last touched, one hour before the declared-attribute contract landed. It produced 11,755 accepted records across 19 batches and then stopped.

Everything since is hand-written per-batch Python: 115 build.py and extract_*.py files under data/omics, 46,231 lines, with lib.py copied 42 times in 11 drifted versions and zero imports from scripts/omics. There are 19 files in scripts/omics/extract, of which batch.ts, pdf.ts and tables.ts are shared helpers, so 16 are per-benchmark extractors.

Four measurements force the shape

  1. The one deterministic value check caught nothing. In the 2026-11-15/16 pass, 13 of 13 batches needed a correction. Across the 11 batches that ran batch -- check-values, no run reported not_in_row, wrong_column or overclaimed_in_row, and five reviews state the output was byte-identical to the extractor's. In two of the eleven (ladon, torchcraft) the parser resolved nothing usable. Of 19 recorded defect classes, 16 were caught only by a human or agent re-reading the source, 2 by gates already in the pipeline, 1 by a bespoke script written for that review, 0 by the value check.
  2. The one locator grammar is a regex. scripts/omics/batch.py:30-31 parses 20,540 of 52,278 stored result locators (39.3%), and check-values has been run on 14 of 194 batch folders because docs/collection.md makes it an optional review step.
  3. Semantic validation is absent. The skos:scopeNote text on unit concepts is read by no code, metric_direction is never compared with the metric's rb:defaultDirection, and nothing compares numeric_value with printed_value.
  4. No check had a backlog number. The reviews name three automatable clusters: comparability-field normalisation (728 records), locator resolution (76) and groundedness of prose and source-reported metadata (187). None had a count of how many stored records violate the proposed check, and the facts brief says plainly that that number is what decides build order.

Where issue #228 is wrong

#228 states the gap correctly: nothing records which assertions of a source were left out, source_locator needs a structured span beside the printed locator, and an extraction receipt should pin tool and model IDs, prompt hashes, temperature and per-stage output hashes. Five of its specifics do not survive a check.

  • The entailment figure is wrong twice. #228 cites "99% entailed by their source sentence". Claimify's Table 1 measures entailment against the combined source sentence, context and question, and reports 99.0% on 12,406 claims against VeriScore's 99.2% on 7,420, with no significant difference (p = 0.145). Claimify's real edge is coverage: 91.8 against 79.0 sentence-level accuracy, 87.9 against 64.7 element-level.
  • The pinned NLI judge repeats a rejected experiment. The Claimify authors ran it and dropped it: the premise, question plus context plus sentence, exceeded the 512-token limit, and the NLI model conflicted with human labels in 32 and 12 of 80 cases against 5 for an LLM prompt. Every pinnable sub-1B judge carries the same ceiling.
  • Docling cannot meet #228's own first driver. Its charspan is item-local; open issue #4217 shows the span exceeding the item's own text length, reproducible without a PDF; #3329 shows the layout model classifying the same PDF differently on macOS ARM and Linux x86_64 at identical versions on CPU; #3401 shows TableFormer dropping row labels on continuation pages.
  • Option 2 is obsolete as written. FEVERFact's fine-tuned models were never published, the repository README is still anonymised review text, and the repository carries no licence, so it cannot be redistributed.
  • The counts are stale. #228 cites 107 per-batch scripts and 19 per-benchmark extractors. Measured now: 115 per-batch scripts under data/omics, and 19 files in scripts/omics/extract of which 16 are extractors.

The stage shape #228 borrows from Claimify, select then disambiguate then decompose, is kept. The claim to Claimify's measured numbers is not, because a reimplementation that changes the model is no longer the measured method.

What the external routes close off

Claimify has no code. Its evaluation set is published under CDLA-Permissive-2.0, its numbers are bound to gpt-4o-2024-08-06 with a 2-of-3 vote at temperature 0.2, and its successor VeriTrail also ships none. VeriScore and IBM's FactReasoner are genuinely Apache-2.0, but they are built for open-domain factuality over model output and emit no offsets.

On the substrate: the repository's hashed pdftotext -layout text is the only deterministic anchor it has, and the 2026-11-16 gpn-msa review already ruled that the text layer, not the publisher's bytes, is what must be pinned. That review measured bioRxiv rotating between two container variants at identical byte length while the text layer stayed byte-identical across all three downloads.

Options

ADeterministic first: a validator pack over a typed locatorSpine of the decision

Replace the single value check with fourteen model-free checks over a typed locator that carries byte spans into a pinned derived text layer. Publish the measured backlog as a pinned baseline and ratchet it. One model stage, admitted only on a byte-span match. Freeze the 115 scripts and promote the shared pieces.

Pros

  • The only design that measured anything new, and five of its seven headline numbers reproduce.
  • Attacks the largest clusters first and needs no source reading to raise roughly 26,000 rows for triage.
  • The first PR is report only, writes nothing to the store and takes days, not weeks.
  • The ratchet makes a report-only PR still bite, on growth rather than on the backlog.
  • Cheapest to build and easiest to reverse: nothing in the first PR touches a record, a vocabulary or the ontology.

Cons

  • Its first stated reason for freezing the 115 scripts is false. No derivation in the store points under data/omics.
  • Two of its baseline numbers, C3 at 170 and C5 at 19,374, do not reproduce from its own prototype.
  • It names byte offsets while calling them TextPositionSelector, which counts code points.
  • It plans a prov:Activity extraction node without noticing that the generated declarations filter prov: out, so its field properties would silently never be declared.
  • It admits six of the 19 classes stay human, and those six produced much of the scientific content of the last pass.

BStandards maximal: make the span the primitiveGrafted in

One hashed text layer per artifact, every value and claim anchored to a W3C Web Annotation selector pair, a PROV-O typed extraction activity, the locator contract inverted so the structure is authored and the string rendered, a deterministic token-coverage gate in place of the NLI judge, and a four-part evaluation harness with a release gate.

Pros

  • Best standards quality, and verified against the generator rather than asserted: the rb: early return, the slice(3) class handling and the prefix allowlist were all confirmed in the code.
  • Dual code-point and byte offsets, with the rule that the layer is never Unicode-normalised, is the right answer for a decade-durable span, and it is the only design that noticed the problem.
  • A mandatory TextQuoteSelector turns a poppler upgrade into relocated_by_quote rather than span_wrong.
  • RFC 7111 and RFC 6901 fragment selectors fit the 15,000 non-table locators exactly.
  • An immutable prompt registry with first_used_release keeps a 2026 receipt meaningful after the model is withdrawn.

Cons

  • Its first gate, 97.4% typed to a resolvable kind, is a weak predicate and is unmeasured. 18.5% of locators can be typed loosely and resolve nothing.
  • Its stricter test, a 90% byte-identical round trip, is the real one and is also unmeasured.
  • Six PRs, about 4,500 new lines, six to ten weeks.
  • Its second PR touches mapping.json, rb.ttl, context.jsonld, rb-attributes.ttl and attribute-shapes.ttl at once against an in-memory rdflib build.
  • It is honest that the standards half catches no defects, which also means a large share of its budget does not move the defect rate.

CMeasurement first: the instrument before the methodTwo controls taken

Collect the scattered reviewer re-reading files, metadata-correction claims and value-check adjudications into one gold set under data/gold, build a harness and seven gates in scripts/eval, then admit extraction methods behind a registered interface only when they pass published gates.

Pros

  • The best diagnosis of the institutional failure: both previous lanes failed for want of measurement, not of method.
  • The only design that puts label reliability first, with a Cohen kappa floor of 0.90 on 60 re-labelled items and a stated kill.
  • Its honest finding is the most useful single number any design produced: zero mismatches among 1,591 keyed re-read rows.
  • Its isolation argument is verified: nothing under data/gold can move a release ID.
  • Method registration with a report naming its gold_digest turns a forgotten re-run into a red build.

Cons

  • Two weeks of agent curation plus one week of harness before any defect is prevented, and the gates it would then enforce are the checks option A ships as a report first.
  • 728 of its 1,139 labelled defects are one class, so recall on everything else rests on between 0 and 187 instances.
  • Every label comes from one reviewer agent, including the 1,591 rows it treats as ground truth.
  • 991 labels have to be recovered by hand-verified inversion of 22 reviewer scripts written to be applied once.
  • Its own first pass can kill it, and the stated fallback, a human-labelled seed of 100 items, is a different and more expensive design.

DAdopt a published claim-extraction method

Reimplement Claimify, or adopt FEVERFact, VeriScore or FactReasoner, and add a pinned NLI judge. Rejected on the facts all three designs agree on, set out under "Where issue #228 is wrong" above. No design was written for it.

Decision

Adopt option A as the spine. Graft option B's span, locator and prompt-registry conformance onto it. Take two controls from option C, and no gold-set curation project.

1. The span substrate is a layer registry over the hashed derived text

A layer is a byte-exact derived representation of one artifact, produced by one declared command from bytes whose SHA-256 is pinned. All addressing, all spans and all resolution happen against a layer. Five layer kinds with one pinned builder each: pdf_text (the existing readPinnedPdfText, pdftotext -layout -enc UTF-8 - - with verified bytes on stdin), jats_text, sheet_tsv (the promoted rawxlsx.py), delimited and json.

Each layer gets one line in data/omics/<batch>/extract/layers.jsonl with layer_id, source_id, artifact_sha256, layer_kind, tool, tool_version, argv, builder_sha256, layer_sha256, bytes, lines, built_at and sanity. This replaces hash_scope as the machine-readable record of what a hash covers, hash_scope being free prose on 587 sources and read by no code; the strings themselves are kept and not rewritten, which is ADR 0003's call. A layer is never rebuilt in place: a fix adds a new layer_id.

One hash, one home. The layer bytes are a single object in ADR 0004's content-addressed store at layer: text-layer; layer_sha256 is the same hash ADR 0003 records as that capture's evidence identity; and this file is a generated projection of those capture entries for the sources a batch cites, checked byte-equal in CI rather than hand-written. Nothing here stores a second copy of a layer or a second name for its hash.

Offsets are recorded twice and both are checked. start and end are Unicode code point offsets, which is what oa:TextPositionSelector counts; byte_start and byte_end are UTF-8 byte offsets, which is what the checker slices. The layer is never Unicode-normalised, because NFC would move every stored offset when an ICU version changes. Normalisation lives in a versioned comparison function named on every check result. Every resolvable locator also carries an oa:TextQuoteSelector with exact, prefix and suffix at 48 code points.

A layer sanity gate runs before extraction and records pass, suspect or fail from the U+FFFD count, the printable ratio, the digit-to-alphanumeric ratio, a punctuation-run mojibake signature, and the page-break count against pdfinfo. No record, claim or candidate may cite a layer at fail. bacformer version 2, which rendered 0.81 ± 0.07 as +.)! +.+( and had a conclusion drawn from it anyway, must come out fail.

2. The locator becomes a key-value selector language

The grammar is anchor+ address? selector* qualifier*, with an open dim on selectors. The open dimension is the measured reason the current grammar fails: half the failing locators select a row by a composite source-specific key (depth, Sequence_Identity, Algorithm, caller, platform, Variant_Type), which is how machine-readable result files are keyed. A closed dimension list recreates the present failure.

The published metric is fully addressed: an anchor, a row-identifying selector or direct address, a column-identifying selector or direct address, and no residue after qualifier stripping. Addresses use the standards that already define them: A1 notation for sheet cells, RFC 7111 for CSV and TSV row and column references, RFC 6901 JSON Pointer for JSON. Those three cover the 15,000 non-table locators.

For new batches the structure is authored and source_locator is rendered from it, and the loader requires renderLocator(locator) === source_locator byte for byte. source_locator stays declared as text and is never rewritten. There is no backfill: parsing a legacy locator produces a report row, not a record edit. A new locator must assert expected_row_labels and expected_shape, and the resolver refuses a caption match whose window contains another caption. That is the fix for the class where batch -- table returned Table G2's body for a Table G1 request with no warning.

Parse coverage and resolution coverage are always reported separately. Resolution is bounded by archived bytes, not by the grammar: 7 batches hold a derived text layer today. The resolver carries artifact_not_held as a recorded status, never a failure for a legacy record and a hard failure for a new batch.

3. Deterministic checks are the defect-catching half, and they ship first

A new directory scripts/omics/checks/, one module per check, each a pure function (records, layers, vocab) => Finding[], each rerunnable with no network and no model. Fifteen checks: unit for metric, direction against rb:defaultDirection, printed against numeric, qualifier shape, column coherence, locator resolution, table identity, groundedness, duplicate artifact, citation metadata, arithmetic re-derivation, recall sweep, normalise or refuse, receipt binding, split-study candidates.

Six things stay with a reader and get candidate surfacing rather than automation: the truth of a stated aggregation, whether a rate's increase is an improvement, which model a configuration configures, whether two sources are one study, whether a record's scope note over-reaches, and whether a sentence is worth recording at all. A design that implies otherwise is lying, and this one does not.

No pinned NLI judge, in any tier, as a gate. A grounding model may prioritise the reviewer queue. Its promotion to a gate is conditioned on three stated measurements: 95% of premises inside 512 FactCG tokens, at most 12 conflicts of 80 on the Claimify human-agreement check, and bit-identical logits across two CPU fp32 runs. None of the three is measured, and the design works with none of them.

4. Groundedness is a token-coverage gate, not substring matching

A prose claim's content tokens must be constructible from its own spans plus a closed connective lexicon at data/vocab/connectives.txt. The gate is 1.0: a single uncovered content token is exactly the defect. Sentences about the record's own evidence state are marked record_scope and are out of scope, because they are not claims about the source.

connectives.txt and the statistic-token pattern set are reviewed data files carrying a version recorded on every check result. Adding a word to the lexicon weakens the gate, so a change bumps the version and needs a dated review. In version 1 the gate runs as a queue sorter with its failures reported, and flips to blocking only if the pilot's tier_b_share is at or below 0.20. bioemu2's substring predecessor matched 42 of 75, so the risk that legitimate claims fail is real and is measured before the gate bites.

5. One model stage group, five stages, and a receipt that does not overclaim

scripts/omics/extract/claims/: index (deterministic sentence and paragraph index with byte offsets over the pinned layer, segmenter versioned by builder_sha256), select, disambiguate and decompose (the three model stages, temperature 0, one completion), ground (deterministic byte-span verification, where a mismatch is rejection with a diff, not a warning) and map (candidate to record field through a committed field map; no mapping is unmapped with a reason). Abstention is a first-class output with a reason from data/vocab/missingness.ttl plus one new concept ambiguous. Nothing defaults and nothing nulls.

Prompts live at prompts/extract/<stage>.v1.md and are immutable once a release references them, with prompts/extract/registry.json mapping sha256 to path, stage, version and first_used_release, and a CI test that fails if a referenced prompt's bytes changed or the file disappeared. The receipt at data/omics/<batch>/extract/receipt.json records pipeline_sha256, the layer with its transformation and sanity verdict, and per stage the model_id, prompt path and hash, temperature, call and token counts, input and output hashes, candidate and abstention counts and span rejections.

The determinism boundary is stated in docs/extraction.md rather than left to inference. The three model stages are verifiable by hash and are not reproducible by re-running. Stage 4 and every check are deterministic, and they are what a reviewer reruns. The claim the repository makes is that a reviewer on a fresh clone can re-verify every stored span and value with no language model. That is weaker than "the pipeline is deterministic" and stronger than what docs/release.md:16 can say today.

6. Candidates are files, never records

data/omics/<batch>/extract/ gains candidates.jsonl, checks.jsonl, questions.jsonl, coverage.json and stages/<stage>.jsonl. No new record status: publicRecords (scripts/omics/schema.ts:140-165) blocks only excluded and disputed plus results outside source_checked, reproduced and superseded, so a candidate-ish status would be exported to the published bundle. A candidate that is not a record cannot leak.

The reviewer promotes with npm run candidates -- promote, which renders accepted candidates through the repaired buildBatch, writes rejected and out-of-scope candidates into coverage.json, and refuses when the reviewer agent concept equals the extractor agent concept. tests/review-independence.test.ts makes the two-pass rule a gate rather than a skill instruction.

7. Coverage is measured per layer, with an arithmetic identity

A statistic-token sweep over the layer, with every hit disposed exactly once as mapped, out_of_scope (reason from a new data/vocab/scope-reason.ttl) or gap (named in notes.md and in a gap record). records -- add refuses the batch when statistic_tokens_found does not equal mapped + out_of_scope + gap, when cells_in_extracted_tables does not equal cells_recorded without a per-cell reason, or when unreviewed > 0. This is what GPN-Star needed: its notes said three places print numbers and all three are extracted in full, while Fig. 3e printed r = 0.47, P = 0.0072.

Source-level coverage becomes an extraction_coverage node on the source record, not an overload of rb:Coverage, whose meaning is items scored per run and which sits on 1,642 results. The docs state plainly that it counts statistic tokens, not meaning: a source can read 1.0 and carry a wrong unit on every result.

8. The 115 Python scripts are frozen, not deleted and not rewritten

maintenance/extractor-freeze.json lists all 115 paths with line counts and sha256, plus the 42 lib.py paths and their 11 digests. tests/extraction-lane.test.ts fails a PR that adds a lib.py, rawxlsx.py, jats.py, ooxml.py, parse_tables.py, build.py, build_batch.py or apply_review.py under data/omics at a path not in the freeze list.

The reason is 213 distinct added_in values naming batch directories and 154 dated reviews citing those files by path and never edited after merge. It is not a derivation-hash dependency: the store holds one derivation.script value, on 59 results, and it is not under data/omics.

Four shared pieces are promoted to scripts/omics/extract/py/: sheets.py from rawxlsx.py (byte-identical in all 11 copies, so a move), jats.py and ooxml.py (5 copies each), and lib.py as the diffed union of the 11 versions, with the per-version behavioural differences recorded in the PR body. A new batch may keep its own extract/source.py capped at 300 lines holding source specs, table expectations and concept mappings only.

buildBatch is repaired, not replaced, because it is the only record-contract-shaped renderer in the repository: object-valued missing_metadata entries, uncertainty omitted with a reason instead of null, review.method as an array with note not notes, a declared uncertainty type instead of reported_plus_minus_type_unresolved, and writeBatch's hardcoded data/omics/reviewed/<key>-2026.jsonl and literal 2026-09-18 receipt name replaced by the batch-folder layout. .agents/skills/extract-evaluations/SKILL.md step 3 and docs/collection.md section 4 are fixed in the same PR, because they point agents at a path that cannot produce an acceptable batch.

9. The language seam is one file, and the decision has a reversal condition

The grammar lives once, in TypeScript at shared/omics/locator.ts, because records -- add must validate a locator object in-process inside loadRecords over 93,187 records and cannot shell out per record. The resolvers stay in Python at scripts/omics/extract/py/resolve/, one backend per layer kind, because those parsers exist and are proven over 194 batches. The seam is extract/cells.jsonl plus candidates.jsonl, whose JSON Schema is generated from the zod schema and committed with a CI test that regeneration is a no-op.

This reverses if the resolver work turns out to be more than about 70% of the total parsing code and the TypeScript side reduces to schema validation. In that case the grammar moves to Python, the loader validates the stored object against a zod schema, and the renderLocator round trip is the cross-check.

10. Measurement is built from what exists, not curated first

  • The validator pack's own correctness test is reproducing the 14 existing value-check.tsv files. In the first PR this is the parse split only: the 551 locator_not_parsed rows must be exactly the rows the ported regex rejects and the other 1,881 exactly the rows it accepts. Row-for-row agreement on in_cell against in_row becomes an acceptance test when the resolvers land, because that status needs a resolver.
  • Seeded mutations are the only way to measure value-transcription sensitivity, because there are zero real instances: all 1,591 keyed re-read rows are matches. Seven deterministic generators, each drawn from an experiment the repository already ran by hand, are a 300-line module and a report, not a gold set.
  • data/omics/checks-baseline.json carries the pinned finding count per check plus the implementation commit and date, and tests/checks-baseline.test.ts fails when a store change raises any count. That test is in this commit, so option (a) of question 2 is the policy in force until the owner rules otherwise: an evidence PR that raises an inherited count fails, and the author either fixes the finding or raises the baseline in the same PR with a dated review. Baselines are pinned from the implementation's own first run, not from a prototype's numbers, because two prototype numbers did not reproduce.

Option C's 1,200-item gold set, seven gates, method registry and gold_digest discipline are not adopted now. They become the right next decision if, after the pilot, the C1 and C5 hand audits show the checks cannot be made precise enough to gate.

11. Schema and ontology changes, with the generator trap named

New declared attributes: locator and spans on result, claim and the other 12 kinds carrying source_locator; layers, text_layer and extraction_coverage on source; extraction on result and claim. New node types rb:Locator, rb:Span, rb:TextPositionSelector, rb:TextQuoteSelector, rb:FragmentSelector, rb:ExtractionActivity and rb:ExtractionCoverage, all rb:-prefixed because nodes[e.node].class.slice(3) requires it.

PROV-O joins as a seventh pinned import with a six-term subset, and the extraction node is typed rb:ExtractionActivity rdfs:subClassOf prov:Activity. source_ids stays on dcterms:source, honouring the rejection recorded at data/ontology/mapping.json:244. Using oa: and prov: properties as node fields takes about 20 lines of generator change: both prefixes added to the allowlist at scripts/kg/attribute-terms.ts:166, and declare at :175 extended with an external-prefix allowlist that emits label and comment declarations into a new generated data/ontology/external-terms.ttl. Without that change the new field properties are silently never declared, which is the failure review.receipt, review.artifact_sha256 and review.retrieval_url already demonstrate: they exist on records and not in the graph.

reviewSchema is .strict() with 12 keys, so adding assertion_method (ECO_0000203 for automatic, ECO_0000218 for manual, terms already pinned and already used this way on rb:Discrepancy) is a real schema change and must be added to the review block of mapping.json in the same PR.

New vocabulary: rb:allowedUnit and rb:discouragedUnit on metric concepts; model-version concepts in agent.ttl, which today has six concepts, one labelled "Claude (model unspecified)", and no human concept; span-containment-check, locator-resolution and adversarial-second-extraction in review-method.ttl; ambiguous in missingness.ttl; and three new schemes locator-kind.ttl, scope-reason.ttl and extraction-stage.ttl. Existing concepts are not retired: 2,732 claims name claude, and retiring it would mean 2,732 record changes.

12. Receipts become enforceable

review.json gets a strict zod schema modelled on scripts/omics/use-cases.ts:21-41, the one receipt the build already enforces, with frozen_extraction_sha256 as a field replacing the prose in scope. records -- add refuses a batch whose receipt is absent or fails the schema, whose files["batch.jsonl"] does not match the bytes being added, whose extract/receipt.json pipeline_sha256 does not match the tree, or whose checks.jsonl holds an unoverridden failure. This is enforced only for batches declaring schema_version 2, because the 168 existing receipts declare 1.0 with two incompatible field sets, and bacformer's already records a frozen hash that disagrees with its own files["batch.jsonl"].

Consequences

What gets better, with numbers

  • The 19 defect classes stop being anecdotes and become pinned numbers in one command. Confirmed today: 5,093 minority-unit results, 1,256 direction findings of which 58 are opposite to the metric's declared default, 338 verdict or vendor tokens in metric_qualifier, 187 duplicate source groups. C3 and C5 are set by the implementation's first run, at 3,436 and 146.
  • Machine-readable locator coverage goes from 39.3% to a measured 72.9% fully addressed, and new batches reach 100% by construction.
  • Four defect classes become impossible to author rather than merely discouraged: a wrong-place locator, a silent wrong-table match, a conclusion drawn from an unreadable rendering, and metadata asserted as source-reported with no span.
  • check-values, run on 14 of 194 batch folders because it was an optional review step, is replaced by a check pack that gates records -- add.

What this costs

  • 39 working days over ten steps, of which 2 to 3 are a human vocabulary pass. About 5,600 new lines plus about 120 changed.
  • Triage of the measured backlog is 20 to 40 agent-days spread over months. The ratchet means it can be paid at whatever rate two people can afford, and it blocks nothing.
  • Model spend is bounded by the prose of one paper per batch, on the order of 40,000 to 150,000 input tokens per source. Every check in the pack is CPU only; the measured backlog ran over 52,278 results in seconds.
  • Layer bytes add roughly 0.5 to 3 MB gzipped per batch, so 100 to 600 MB over the next 200 batches. None of it lands in git: they are objects in ADR 0004's store, whose eviction gate keeps new binaries out of the tree, so the cost is archive storage rather than clone weight.
  • Standing cost: one more command and two more files per evidence PR, about 60 seconds of CI, and a baseline update on perhaps one PR in five.

What gets worse or stays broken

  • Resolution coverage is hostage to the archival decision, which is ADR 0003's rescue waves, not to this one. 7 batches hold a derived text layer, and 45.2% of evidence citations (47,081 of 104,243) rest on a source whose bytes are not stored. For most legacy records the honest status is artifact_not_held forever, and the locator object is a well-typed pointer at nothing.
  • Six of the 19 classes stay human: aggregation truth, rate semantics, configuration identity, companion_of, scope over-reach, and whether a sentence is worth recording. Those six produced a large share of the scientific corrections in the last pass. A design judged on class coverage scores this well; a design judged on whether the next pass needs fewer human corrections may not see much change.
  • A grammar that parses more strings also parses more into the wrong structure, and resolving silently to a plausible neighbouring cell is worse than failing to parse. The defences are the cell-plus-label cross-check, expected_row_labels and expected_shape; a locator with no internal redundancy has none. Measure before gating resolution: resolve all 38,103 parseable locators against the sources whose bytes are held and compare wrong_column and not_in_row rates against the 14 existing value-check.tsv files as the control.
  • C1's 5,093 rows may be mostly store convention that was never written down. f1-score alone splits 2,603 percent against 928 fraction and 434 unitless over 3,965 results. If a 100-row hand audit shows above 20% false positives, C1 can never be a gate, and the real deliverable is writing the convention into metric.ttl.
  • One shared library means one place to break. A bug in the promoted lib.py reaches every new batch where today it reaches one. The trade is worth making at 11 drifted versions, and the promoted union must have its per-version behavioural differences recorded in the PR body, which is a day of unglamorous work that is easy to skip.
  • The repository takes on a serialisation format, jats_text, that it must keep stable forever. builder_sha256 on every layer record and the never-rebuild rule are the mitigation.
  • Figure-only values stay gaps, and published values that rest on OCR of a raster image stay unverifiable at any layer. The coverage metric will show those sources as incomplete, which is correct and will look like a regression against today's silence.

Reversibility

The first PR writes nothing to the store, changes no vocabulary and touches no ontology file, so it reverts by deleting files. The layer registry and the typed locator are additive attributes absent on existing records, which is legal today, so no stored value changes, no provenance line is re-hashed and no past release ID becomes unverifiable. The only one-way doors are the vocabulary additions, which are additive and retire nothing, and the jats_text serialisation.

Open questions for the owner

Two are open and are why the status is Proposed. Each is a closed choice, and each blocks a specific step. A third, where the layer bytes live, was asked here and is answered elsewhere; it is kept below as closed so a reader of all four records does not find it open in one and decided in another.

Question 1 · closed, answered by ADR 0004

Archive the gzipped derived text layer in git under data/omics/<batch>/artifacts/, or publish layers as release assets and keep only the hash manifest in git?

Release assets. ADR 0004 decides the substrate: a layer is an object in its content-addressed store at layer: text-layer, published on a shard tag, with the manifest committed at data/archive/objects/<0-f>.jsonl. Its eviction gate refuses a new tracked binary over 1 MiB in git, so the in-git branch is not available anyway. ADR 0003 is where a layer's identity is recorded, as the evidence identity on a capture. The layer registry below holds the same hash, not a second copy of the bytes, and artifact_not_held resolves against that one store.

Question 2 · option (a) is in force as shipped, pending the ruling

Does the ratchet in data/omics/checks-baseline.json (a) block any PR that raises a finding count, including an evidence PR that only adds records to a benchmark whose unit convention is already inconsistent, so the author either fixes the inherited finding or raises the baseline with a dated review, or (b) block only PRs that change scripts/omics/checks/ or the vocabulary, and stay advisory on record-adding PRs?

tests/checks-baseline.test.ts is in this commit and implements (a): it runs the seven checks over the whole store and fails when any count rises above its pinned baseline, whatever the PR touched. So (a) is the policy in force, not a proposal, and the ruling either confirms it or narrows the test.

What (a) costs, stated plainly: an evidence PR that adds results to a benchmark with an existing minority-unit convention fails, and the author either fixes the inherited finding or raises the baseline in the same PR with a dated review saying why. That is expected on roughly one PR in five. Option (b) risks the backlog growing faster than triage, and moving to it is a change to this test's scope, which rules it to the files a PR changed. It is not a change to any check: the checks are report severity either way and nothing here gates records -- add.

Question 3 · blocks step 6

Commit to a human pass over all 275 metric concepts filling rb:allowedUnit and rb:discouragedUnit, after which C1 can become a gate, or leave C1 at report severity permanently and treat the 5,093 minority-unit findings as a triage queue only?

The pass is 2 to 3 days, one off. C1 cannot be a gate without the vocabulary, and the measured ambiguity is real: f1-score splits 2,603 percent against 928 fraction and 434 unitless, which is partly a convention nobody wrote down rather than 3,965 errors.
